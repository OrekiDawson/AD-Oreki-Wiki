# 反物质维度MOD Wiki:知识库规则

> GitHub 的原始源码、Commit、PR、Run 与设备实证才是事实依据。Quartz 站点只是衍生展示层。

## 总原则：以中文百科的标准编写

本站面向**人类读者**，不应成为给自动化工具阅读的流水账。参考中文维基百科重视的**可供查证、中立叙述、避免无证据推断、清晰体例**等理念，但它是 AD-Oreki 工程知识库，**不是维基百科的复制品，也不机械照搬其收录标准**。对本项目的技术事实，原始源码、构建报告及实际设备测试属于可以直接引用的一手材料。

**准确第一，易懂第二，完整第三，自动化最后。** 内容、引用与历史事实如有冲突，不能为了让文章流畅而掩盖矛盾。

### 可读性与趣味性是正式质量目标

准确性是底线，可读性是基本要求，趣味性是重要质量目标。本站既是查询工具，也应当是值得主动翻阅的中文游戏百科：让读者理解机制如何运作、为什么这样设计，以及它与其他系统有什么有意义的联系。

- 使用自然、有节奏、有思想的简体中文，主动删除明显的 AI 腔、报告腔、公文腔和无意义总结。
- 根据主题自由组织结构，不强制套用统一模板。可以使用有来源的比喻、机制揭秘、历史背景、数学趣闻、设计取舍、真实故障案例、源码片段或流程图，让复杂内容更容易理解，也更值得继续读下去。
- 趣味表达必须服从事实。不得虚构游戏机制、开发历史、技术原理或玩家体验；不滥用感叹号、网络梗、Emoji、夸张修辞和刻意卖萌，也不能让趣闻喧宾夺主。
- 玩家条目应把操作、因果、数值和设计趣味放在同一条清晰叙事中；开发者条目应同时解释代码做了什么、为什么这样实现、有哪些取舍和可迁移的技术经验。历史报告、PR 流水账、审查记录和机器摘要放入附属资料，不代替正文。
- 原版译文不适用本站自由发挥的趣味改写：必须忠实原文段落，统一术语，保留公式、数值、修订、版权与署名；本站的解释、趣闻和 MOD 差异放在译文之外的相关条目中。

**本站的收录边界**：参见专门方针[反物质维度MOD Wiki:本站不是什么](/wiki-not)。百科正文不充当 PR 流水账、宣传栏、AI 草稿集或无解释的资料堆；但经核实的玩家攻略、开发者操作手册和可复核的原创技术研究是本站应当提供的内容。

### 正式规则的名称与公开位置

- **正式规则及专题方针页使用命名空间式标题 `反物质维度MOD Wiki:标题`。** 例如 `反物质维度MOD Wiki:知识库规则`、`反物质维度MOD Wiki:本站不是什么`。方针页的 `title` 和一级标题保持一致；使用英文半角冒号，后面不加空格。
- **普通知识条目不添加前缀。** 标题与正文都采用自然、易懂的简体中文，例如“存档兼容与自动保存”“阶段门禁”；技术标识符、专有名词、API、哈希、命令和文件路径保持准确原样。
- 全站显示名称统一为“反物质维度 MOD Wiki”，不等同于规则页标题。旧有 Markdown 文件、URL 和 Wiki 内部链接保持稳定，不为展示名称而改动。
- 根目录的 `wiki-rules.md` 是**全站编辑规则总纲的唯一权威来源**；[本站不是什么](/wiki-not)为其配套的内容边界方针，不能在别处另建相互冲突的规则副本。网站首页、左侧根目录和全站页脚应保留总纲链接。旧 `docs/CONTENT_QUALITY.md` 只作为兼容入口，不再单独维护另一份规范。

### 一、全部使用规范的简体中文

- 面向读者的**标题、导语、章节、正文、图注、表头、按钮文字、摘要、标签说明和示例讲解**使用简体中文，标点符合现代汉语习惯。避免中英夹杂的流水账式句子与英文模板标题。
- Kotlin、AGP、DEX、ABI、GitHub、Commit、SHA-256、源码标识符、方法名、完整错误消息、命令、文件路径、专有名称和编程语言语法保持真实拼写，**首次出现时用中文解释**，后文用同一译名。不得为“全中文”而翻译、改写 API、字节码描述符、哈希值和代码。
- 技术系统要求的英文机器字段，如 Quartz 的 `title`、`description`、`tags`，保留标准键名，但**对应值使用简体中文**；分类标签中不可替代的程序标识可保持原样。
- 不以“P0 已闭环”“AGP PASS”这样的缩写堆叠代替解释。先说实际含义，再展示项目使用的状态代码，例如“新档 180 分钟通关：失败（FAIL）”。
- 避免“史诗级”“彻底完美”“显然”“毋庸置疑”等宣传口吻，不揣测开发人员意图，不把模型推测当作实验结论。

### 二、像百科一样讲清楚，但不牺牲技术准确性

1. **先解释是什么**：开头一至三句话定义主题、使用场景与当前结论。普通读者不必先理解混淆类名就能读懂文章在讨论什么。
2. **再解释为什么**：按因果顺序说明背景、问题、工作原理、影响范围，首次使用的术语提供通俗解释，必要时附准确技术细节或小例子。
3. **最后交代如何验证**：给出可以定位的源码、报告、复现步骤、通过和失败条件，以及尚未完成的部分。百科式叙述与操作步骤可并存，但不要只贴命令不解释用途。
4. **用自然段为主**：表格用于真正的对比和数据，列表用于步骤或简明列举。禁止每个句子都写成一个要点，禁止将整篇文章做成测试清单、CI 日志或大量状态徽章。
5. **遵循主题边界**：一篇文章只承担一个明确的主问题。复杂内容分成可独立阅读又相互关联的条目；拒绝空白占位、机械拆分和重复定义。

### 三、可供查证与客观叙述

- 对**关键结论、数字、版本、时间、成功/失败状态**，在相关陈述附近附**可点击的原始来源**。优先固定 Commit 的源码/报告链接，必要时补充 PR、Issue、Actions Run 和设备证据。一个页尾总 SHA 不能代替逐项引用。
- 区分：**已证实事实**（来源与测试明确）、**来源作者声明**（有记录但未独立验证）、**合理推断**（写明前提）、**待核实问题**（不能宣称 PASS），以及**已被推翻的历史结论**。
- 同一问题出现相反结论时，说明原始时间线、适用版本、证据级别和冲突范围，不删掉有追溯价值的旧结论，也不将新日期自动等同于正确。
- 项目自有的一手设备报告、源代码和 PR 是工程事实的首要来源；一般软件原理或第三方产品行为则优先引用官方文档或可靠独立资料。**不允许 wiki 条目互相引用，构成没有原始证据的循环证明。**
- 每次技术核实时，应确认“已编译”“能安装”“功能已验证”“达到 180 分钟目标”“可正式发布”是不同结论，不能彼此替代。

### 四、文章布局：正文面向读者

以下只为**一般叙述类文章**提供思路，不是必填目录。开发者专区须根据实际用途选择教程、操作指南、参考或原理说明；禁止按同一目录生成所有页面：

1. **标题与导语**：告诉读者主题是什么、为什么重要、目前是什么结论。
2. **背景和机制**：从通俗解释过渡到精确的技术细节。
3. **当前事实及证据**：必要的比较、数据、可复现步骤和直接引用。
4. **局限与争议**：说明未验证、适用版本或历史修正。
5. **参考资料与相关条目**：可点击的固定来源和 Wiki 内部链接。
6. **专区与检索**：普通玩家正文不嵌入 AI Summary；开发者技术条目可按下方规则提供已审核、默认折叠、带来源的 AI Summary。站内搜索由 Quartz 内建搜索依据正文及元数据提供。

参见 [按用途选择的中文条目样板](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/ARTICLE_TEMPLATE.md)。模板只用作提示，不是机械填空要求；**历史文档不自动批量改格式**。

### 五、编辑与审阅纪律

- 编辑前检查当前 Android/Web 仓库的最新有效来源，以及文章当前引用所对应的版本，避免把过期状态写成当下事实。
- **自 2026-11-17 起停止自动 AI 草稿整理**，不再定时调用模型或自动创建草稿 PR。仅对已明确提出的内容需求按原始证据写作并通过正常 PR 审查；历史未审 AI 草稿继续隔离，不得自动发表。
- 不复制中文维基百科的实际条目文本或格式手册正文。这里只借鉴通用编写原则，引用外部内容时遵守其许可条款与署名要求。
- CI 只对**机器可判断的格式与来源规范**做有限检查；流畅性、解释深度和事实真实性依靠针对性人工复核，不做逐字数、逐标题的繁琐审计。

## 读者体验优先的三阶段编辑与发布制度（2026-11-22）

**本站暂停“每 48 小时必须产出内容版本”的数量和时间考核。** 条目能否公开取决于事实、解释、版权、Lead 正文复审、CI、Kody 与 Pages 门禁，而不是页数、生成速度、模型 Token、Commit 数或 CI 绿灯。修好一篇旧文章优先于批量发布空泛新页；作者自检和事实核查必须记录；发现实际问题或尚未完成 Lead 复审时阻断，不虚构通过或为了交付频率降级。

### 玩家与开发者的真正分工

- **玩家专区**应让读者无需了解项目开发历史，就能回答“是什么、为什么重要、在哪里操作、现在该做什么、下一步如何解锁、哪些情况容易出错”。多提供真实界面名称、准确解锁条件、简明路径和实际例子；以按玩法阶段阅读为主，不把抽象口号、工程门禁、PR 编号、Kotlin/ABI、测试日志或“如何核查源码”作为正文主体。若关乎玩家风险，直接说清风险和备份方法，技术细节通过链接放在开发者专区。
- **开发者专区**必须围绕可完成的开发任务组织知识：从环境上手、模块与调用链，到构建/调试/验证，再到源码参考。PR/Commit/Run 是核验依据而非文章主体，历史与现行实现分开；详细标准见下文“开发者文档质量与重构”。
- **原版 Wiki 翻译**保持原文修订、许可与署名，先忠实逐段翻译再做术语和中文可读性校订；不得擅把 MOD 玩法混入原版，不能因机械的结构检查即声称已审校完成。
- 同一个技术细节只维护一份权威解释，跨专区按需链接；不做大规模机械搬移或删除，不破坏已公开 URL、版权和来源信息。

### 每篇正式新稿或大幅修订的统一门禁

1. **资料整理**：查对原版官方/社区资料、冻结源码和实际 MOD 版本，抽取必要概念、数值、公式、限制与出处，区分已知、未证实和模型推断；不可根据既有 Wiki 二次转述循环引用。
2. **中文撰写**：围绕目标读者的真实问题写自然段，先讲机制/操作再补必要例外；不机械套用“背景、核心目标、如何核查、总结”模板，不用大量表格、开发记录、AI 套话凑长度。对写作模型不作未经比较的能力断言；可在同题样本上选更适合中文百科表达的模型，但需要遵守授权、Provider、费用限制。
3. **作者自检与 Lead 复审**：由撰稿 Agent 完成逐段自检，核实重要事实、数字、解锁条件、出处、术语、读者操作路径和专区边界，并记录适用版本与未运行范围。随后 Lead 必须亲自阅读全部新增或修改的最终正文，复核事实、自然中文、阅读趣味、机制/技术深度、结构、实际用途、译文忠实度与版权；必要时由 Lead 直接润色或退回定向修改。独立编辑审校、人工阅读或另一模型复核可以作为增强项，但不能替代 Lead 复审。未经 Lead 复审必须标记 `EDITORIAL_BLOCKED`，不得合并或发布。Kody、CI 和结构检查不能替代事实核查或 Lead 复审。

审校后的事实错误、玩家无法照着操作、明显 AI 模板腔、文不对题、无来源关键结论或跨专区严重混杂，均足以阻断该条目的正式发布。纯链接或错字等小改动做对应最小检查即可，不要求每次重跑全文审校；历史旧文不因本规则自动删除，但应标明尚未审校的内容状态并分批修订。

《开始游玩》《无限与永恒》《智能自动购买器》已经提出候选稿，#82、#83 另有六篇候选稿。总计九篇均按最新 HEAD 核对数字、实际界面、原版与 MOD 差异、中文自然程度、移动阅读和来源，并根据作者自检与事实核查结果修改；这九篇与其他文章适用同一门禁，不因初稿已经完成、CI PASS 或 PR Ready 就自动合并。独立审稿人不是强制前置，但每篇必须完成 Lead 正文复审；未复审不得合并。详细门禁见本页“玩家专区内容标准与重构”。

## 玩家专区内容标准与重构（2026-11-22）

**玩家专区的任务是让读者真正理解并合法推进游戏，不是展示 MOD 开发记录。** 写稿前须说明目标读者、所在阶段、适用平台/版本，以及本页究竟要解决哪一个问题。禁止在同一篇文章里混写百科、速通路线、开发故障和版本日志。

### 五种写作类型，不套统一目录

| 类型               | 玩家问什么                                   | 合格文章应包含                                                                 | 避免什么                                                   |
| ------------------ | -------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **机制百科**       | “是什么、为什么、会保留或重置什么？”         | 资源来源/用途、准确解锁条件、生产与重置机制、相关系统关系、必要的真实例子      | 仅用“更快成长”、源码符号或技术报告替代机制                 |
| **入门教程**       | “第一次应该在哪里点、怎么做？”               | 前提、实际界面名称、按序操作、正常结果、下一步与易错点                         | 只讲理念、不写操作，或编造按钮                             |
| **分阶段攻略**     | “我在无限/永恒/现实/天神卡住，怎样选择？”    | 适用版本/存档、建议路线、原因、预期效果、替代方案与限制                        | 假定一种路线对所有版本最优，承诺固定通关时间，绕过正常结算 |
| **FAQ 与故障指引** | “按钮不能用、自动化没动作、存档不对怎么办？” | 先做安全检查，再排除真实资源/前置条件，最后收集可复现信息；导入/更新前明确备份 | 直接建议清档、改 JSON、强行跳转、公开私人存档              |
| **原版 Wiki 译文** | “原始修订真正写了什么？”                     | 忠实逐段翻译，保持公式/数值/术语，记录原页和修订、署名、许可及审校状态         | 将 MOD 改动塞进原版，结构检查冒充逐段审核                  |

文章以**最主要读者任务**定类型，可以链接其他页，不强制每页同时具备所有内容。不得统一套写“背景→目标→原理→总结→参考”；必要时用例子、步骤、表格或图示，但它们都应帮助读者理解或操作。

### 按玩家进度组织导航

- 新档和第一次大坍缩 → 无限及打破无限 → 永恒、挑战和时间研究 → 时间膨胀与现实 → 符文、天神与终局。**这是阅读路线，不是强制分钟数。** 玩家应能按自身阶段进入，也能通过搜索找到独立机制。
- 机制百科讲清真实规则，攻略只讲基于规则的选择，FAQ 讲正常限制与异常的区分。相同数值和前置条件尽量由一处权威页面维护，其他页做精简说明和内部链接。
- 正文优先使用玩家可见的界面名称、资源、解锁关系与适量数字。除非解释玩家面临的实际风险，否则不要给玩家讲 Kotlin/Smali/DEX、PR、R 轮次、构建 Run、测试时间线。
- 不以减少“AI 味”为借口删掉数字、警告和来源；去套话 Skill 只能润色表达，改变机制事实必须重新核实。

### 原版、MOD、平台、版本必须分清

1. 原版网页机制按项目冻结上游与可确认的 wiki.gg 原始修订核对，Android 原版按 3.21.0 基线；MOD 规则以当前 Android/Web 各自实际源码、发布版本与必要游戏内证据为准。不能把原版行为、历史构建、未合并 PR 或旧文章文字当作当前 MOD 事实，也不能因为“双端目标一致”就宣称行为已实测等价。
2. 写解锁条件必须核对**资源单位、数量级、挑战完成次数、研究前置和真正结算动作**。例如反物质与无限点数不能混淆，入口出现不等于已有真实结算。调度器受管字段和下一有效 tick 的配置归属，按用户最新规则与两端实际实现分别核对，不照搬过去彼此冲突的“手动优先”与“强制接管”叙述。
3. 真实新档 ≤180 分钟及五阶段节奏是**设计/验收目标**，不代表所有玩家/版本都可保证通关。引用某次记录必须带版本、游戏速度、环境、原始结算和日期；不得为实现目标伪造资源、成就、挑战或结局。
4. 引用原版资料时记录准确页面和已经真实核对的修订号，不能用未核验的 oldid 或机械字符串替换生成坏链接；网络不可达时写明未完成核验，不声称取得 wiki.gg API/HTTP 200。本站原版译文 `STRUCTURE CHECKED` 不等于可验证的玩法证据。

## 开发者文档质量与重构（2026-11-22）

**开发者专区不是开发日报、测试状态面板或 AI 摘要陈列室。** 它的目标是让一个没有参与历史 R 轮次的人，凭已公开的真实仓库、文档与可获得的环境，能上手开发、理解关键设计、找到需要修改的代码、完成对应的构建验证与问题定位。不能靠增加篇数或统一模板满足这一目标。

### 开发者正式正文必须从零重写

开发者正式正文实行全量重写：作者必须从真实 Android/Web 源码、当前构建链和原始技术资料重新建立事实、读者问题、标题、章节与叙述逻辑。旧文章只可作为事实核查线索，不得作为写作底稿；仅替换措辞、调整段落、补链接或拼接旧正文不算重写。旧稿中的历史事实、原始证据、版权信息与有效 URL 进入历史/证据层或以 `aliases` 兼容，不因重写丢失。已按本标准完成并通过 Lead 完整正文复审的文章不重复重写。

正式技术正文不得按 R 轮次、日期、PR、Issue 或 Agent 工作记录写成流水账；不得堆砌 PASS、FAIL、BLOCKED、NOT RUN、Commit、路径而不解释其技术意义，也不得把长期规则、任务书或验收报告改写成文章。避免空泛的“背景/目标/意义/总结”模板和用大量表格、条目替代连贯叙述。历史开发记录归入 `content/developer/history/` 或证据层；正文必须提供机制、设计取舍、调用/数据流、技术难点、使用修改排查方法及可迁移经验。

### 逐页状态是内部交接，不是正文成果

三份重构台账必须按当前实际文件树逐页登记所有 Wiki Markdown 文件，不能只列本轮修改页或沿用过期数量。每行记录标题、路径、规范 URL、专区与内容类型、处理方式、统一进度状态、负责人、PR/Commit、Lead 正文复审结果、合并及线上验收状态；旧入口、历史档案和 AI 草稿分别注明兼容/归档/排除原因。台账只服务交接与发布门禁，不得写入公开正文，也不能替代真实重写、Lead 审阅或线上验收。完成率按“已上线验收的应处理页面 ÷ 全部应处理页面”计算，兼容入口与归档单独统计。

### 并行写作、滚动复审与集中交付

不再限制为单一 Wiki Subagent。Lead 可按文件 Owner 和主题边界并行派发最多 5 名 Subagent，每名一次认领 3–6 篇相关正文，复用同一批源码和原始资料；不得让无冲突的已授权 Agent 在等待外部检查时闲置。Subagent 每完成一篇即可交 Lead 逐篇阅读全文，同时继续同组其他文章；Lead 不得只看汇报、Diff、CI 或 Kody。相关文章集中组成小批量 PR，写作并发与开放 PR 数量解耦，六仓 PR 上限、Kody、CI、合并和线上验收门禁不变。

### 按使用场景写四类文章

| 用途         | 读者在问什么                                   | 合格正文至少提供什么                                                                                                | 常见错误                                                         |
| ------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **入门教程** | “我第一次参与，怎样从零完成一件小任务？”       | 支持的环境与版本、准备步骤、按顺序执行的一个最小闭环、成功表现、失败时去哪里；示例必须可用，不要求覆盖全部架构      | 大篇概述、空命令或无从验证的“运行成功”                           |
| **操作指南** | “我现在要构建、验证、排查或交付，怎样操作？”   | 明确前置条件、真实代码/脚本入口、命令和参数含义、预期产物、失败判断及恢复路径；未在环境执行写 `NOT RUN`             | 只列原则、只有 `<path>` 占位符却叫作一键教程、混淆本地与 CI 权限 |
| **技术参考** | “某个模块、接口、配置和字段的准确约定是什么？” | 源码/定义所在仓库、文件、符号、参数和边界条件、适用 Commit 或版本、与其他模块的准确引用关系                         | 复制整份源码、猜测符号、在许多页面重复同一张表                   |
| **原理说明** | “为什么这样设计，修改它会影响什么？”           | 关键模块与职责、真实调用或数据流、重要取舍与失效方式、支持论断的源码/设计证据；复杂时一张可核对的图比术语清单更有效 | 把抽象口号、缩写表、构建任务列表当作架构                         |

同一技术主题可以有不同用途的页面，但它们须解决不同问题，并从**一个权威事实源**互相链接。无需把四种内容揉进一篇，也**禁止以“背景→工作原理→已确认与未确认→如何验证→历史变化”作为全站开发文档固定模板**。目录由读者问题决定，不由 AI 的常见文章结构决定。纯概念页不强行提供 shell 命令；可执行指南却必须能落到真实文件和操作。

### 内容证据及可执行性

1. **先查仓库，再写命令**：读取本次引用的 Android/Web 最新实际源码、脚本、工作流及现行规则；指明命令在哪个仓库根执行、依赖工具版本、需要何种输入和权限。不得从旧报告推断现行脚本仍存在，不得编造 `gradlew` 目标、环境变量、参数、产物路径、行号或运行输出。
2. **讲清数据和控制流**：架构文章应能把功能对应到真实入口、主要调用链、状态在哪里持有与持久化、失败后如何恢复；仅有“Android 使用 Kotlin / Web 使用 JavaScript”不能算架构。涉及安全、签名、存档等高风险环节时写清不可越过的边界。
3. **来源就近、版本明确**：固定到可点击的 Commit/具体路径，必要时附 PR、Run、报告；动态 `main` 链接不得当作固定历史证据。引用外部 Wiki 记录原始页名及已确认的修订号；如果当前无法直接核验，明确写“源自本站历史归档、实时复核待完成”，绝不伪写 HTTP 200、核对日期或 API 回执。
4. **验证分层**：作者读过代码≠命令已执行≠CI PASS≠设备运行 PASS≠玩家进度合法≠正式发布。操作步骤有**预期**输出时标明“预期”，实测输出才写“实测”，附执行环境及可复核证据；无法运行标 `NOT RUN` 或可解释的 `BLOCKED`，不能靠生成一段命令暗示它可运行。
5. **技术事实归源仓、阅读体验归 Wiki**：大型报告、日志、字节码映射与测试样本仍以 Android/Web 原仓为权威，Wiki 提炼因果关系、定位方法和必要链接，不复制大量多版本事实形成分叉。引用过期结论须说明原适用 Commit、后续更正和现行未知项。

### 开发者作者自检与放行

正式新页或大改须经过：①明确读者任务并读取源仓；②从零重新构思并撰写；③作者完成技术事实、读者任务、路径/命令、版权和未运行范围自检；④Lead 亲自完整阅读最终候选正文。Lead 必须检查事实、来源、中文、趣味、技术深度、结构、实际用途、版权与兼容 URL，必要时直接润色或要求定向整改并复核。Subagent 汇报、Diff 摘要、Kody 或 CI 均不能代替正文阅读；未完成 Lead 复审一律 `EDITORIAL_BLOCKED`，不能合并或发布。Lead 自己撰写的文章执行作者自检并记录范围。操作指南的关键步骤可在授权的相同环境真实运行就记录结果；未运行范围必须显式限制“可执行已验证”宣称。关键错误、凭空参数、过期入口、循环证据或无法完成读者任务同样阻断。

**小改例外**：仅修错别字、链接格式或未改变结论的微小修正，做与 Diff 对应的定向复核即可，不需重跑所有业务测试或强制两位模型重写全文。

## 读者正文与审查证据的边界

**文章是写给人读的，审查记录是写给维护者查的。** 2026 年 11 月的三篇玩家标杆稿曾把 `NOT RUN`、HTTP/API 回执和 `revid` 核对状态重复附在参考链接后，导致正文被审计文字淹没。这类行为属于内容质量回归，不得作为满足来源审查的写作方式。

- **玩家正文**：自然解释机制、前置条件、具体操作与注意事项；保留确实有用的原始链接及适用版本，但禁止给每条引用追加 `HTTP 200`、`API 核对`、`revid 归属证明`、`NOT RUN`、CI/Kody/PR 状态、人工核验流水账或机械重复的“尚未核验”长括号。引用可以在正文就近给出，文末参考资料只按阅读需要整理，不必正文与文末机械重复。
- **事实核验**：关键数字、解锁条件、引用修订号以及外部 Wiki `?oldid=` 与页面标题的对应关系必须实际核对。尚未确认时不得伪造回执或暗示已核实；应修复链接、选择可信替代来源，或将关键内容保留候选而非公开。需要向读者提醒的不确定性应以简短、具体、与玩法相关的自然语言说明，不能用复制内部状态模板代替核验。
- **内部证据**：访问结果、API/修订号比对、未运行项、Kody finding、Check Run、测试时间和来源核对过程，应存于 PR 描述、Review Threads、内部核验台账或对应技术档案。开发者专区只有在执行构建、测试或故障排查确有需要时，才按任务说明准确呈现必要的验证状态与证据。
- **审查意见需要判断**：Kody Balanced 对所有有实际文件改动的 Wiki PR 仍是强制门禁，不能将未运行、`skipped`、等待和失败当作通过；但审查建议不是正文模板。对真实问题进行最小、准确且可读的修复；建议与用户明确授权冲突、要求虚构证据或损害阅读体验时，不机械照搬，应说明理由并给出等效且可靠的纠正方式。内容事实或版权问题使用 `EDITORIAL_BLOCKED`，Kody/CI 等审查阻断使用 `REVIEW_BLOCKED(原因)`，两者不得混记。
- **合并前可读性检查**：人工阅读改动后的完整段落和参考资料，检查中文是否自然、教程是否可操作、是否出现反复核验括号、重复外链与 AI 报告腔；发现污染先定点修正，不为了让 Kody 满意而整篇机械改写。Kody/CI 等外部回执未变化时，记录当前 HEAD 与具体阻断，转做其他独立工作或结束，不空轮询或重复付费请求。

## 什么才算一篇合格条目

正式专题文章必须真正解答目标读者的问题，而不是仅罗列规则或复制开发日志。**下面六项只作为需要时的核对问题，不强制每篇具备所有栏目**；技术参考可以没有操作命令，操作指南必须有可核实步骤：

1. **主题与适用范围**：一句话交代该页能解决什么、涉及哪个版本；只有真的在呈现验收结果时才标 `PASS / FAIL / BLOCKED / NOT RUN`，普通概念页不必强插状态表。
2. **问题、影响范围和原理**：如协程 ABI，说明触发条件、调用边界、关键描述符、根因和解决机制；如存档，说明写读路径和跨构建区别。
3. **可操作资料**：相关源码文件、实际路径、复现条件、必要命令（不含密钥或私有路径）、最小验证步骤及已知限制。
4. **直接证据链接**：优先指向固定 Commit 的具体文件/行，至少提供原始 PR、报告或 GitHub Actions Run 的可点击 URL。不能只写 `PR #88` 或一个无链接 SHA。
5. **结论历史**：旧判断、否定它的证据、当前有效结论，不覆盖或删除历史；明确「已测」「推断」「尚未测」。
6. **关联与版本边界**：仅连接有助于理解或执行当前任务的资料，解释 Android/Web 差异；不要把一次本地 AVD PASS 扩大成完整发行门禁通过。

不同页面不必死板套模板，但不能用空泛口号、无证据的 PASS、无目的的表格填篇幅。**不以页数、字数、AI Token 数或知识图谱节点数评定质量。**

### 内容验收等级（适用于原版翻译与外部资料整理）

原版 Wiki 翻译与整理类页面必须如实标注**做到哪一步**，不得把「结构与原站一致」写成「已完成内容审校」：

| 等级                    | 含义                                                                      | 记录要求                                            |
| ----------------------- | ------------------------------------------------------------------------- | --------------------------------------------------- |
| `TRANSLATED`            | 正文已翻译（可含机器辅助），尚未充分核对                                  | 页面 frontmatter 与清单一致                         |
| `STRUCTURE CHECKED`     | 章节、小节、表格、公式、来源/许可字段与原站结构一致；**明确不算语义审校** | 结构核对记录（可为机器比对）                        |
| `REVIEWED`              | 已对照原文**逐段**审校，确认术语、数字、公式、解锁条件与语义无明显缺陷    | 必须有页面级审校记录（`docs/translation/reviews/`） |
| `VERIFIED AGAINST GAME` | 关键机制/数值已与游戏源码或真实运行证据交叉核实                           | 必须能点到源码/证据与核对结论                       |

- 只有 `REVIEWED` 与 `VERIFIED AGAINST GAME` 计入「已审校覆盖率」；`STRUCTURE CHECKED`、`TRANSLATED` 单独统计，不计入。
- 没有逐段审校记录时不得标 `REVIEWED`；没有源码/运行证据时不得标 `VERIFIED AGAINST GAME`。机器翻译、格式检查、字符串比对都不等于内容审校。
- 翻译专区的具体字段与清单口径见 [docs/translation/POLICY.md](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/translation/POLICY.md)；本页等级定义与 POLICY 冲突时以本页为准。

## 普通条目与历史归档：反日志化规则

本站的正文是**技术百科**，不是开发更新日志。以下规则同时适用于人工编辑与 AI 辅助整理，并作为 CI「反日志化」检查的判定依据。

### 一、普通条目必须围绕独立知识主题

1. 一个普通条目回答一个明确主题，并尽量覆盖：**这是什么、为什么存在、如何工作、已确认什么、有哪些限制与常见问题、如何核查、进一步阅读**。读者应能在不理解更新日志的前提下读完。
2. **禁止在普通条目正文无限追加开发轮次日志**：不得把「R101 做了什么、R106 修复了什么」按时间或轮次堆成章节；不得用逐日改动、Release Notes、PR/Commit 汇总、每次 CI 结果或版本发布流水账充当正文。
3. 开发过程与原始记录归 Android/Web 仓库的 `reports/`、GitHub PR/Issue 与 Actions Run；**版本变更归独立历史记录**；**长期有效的技术结论提炼进专题条目**。
4. 修改事实时**更新原条目**，不为同一事实新建重复页面；同一结论不复制多份。旧结论被推翻时保留必要的「旧结论 → 新证据 → 当前判断」说明，但不要把整条时间线写进专题正文。
5. 普通条目**不以日期或轮次作为主要组织方式**；不设统一字数门槛，**质量优先**，禁止为增加文章数量机械拆分或写空占位。
6. 新条目必须能**脱离更新日志独立阅读**：不知道任何 R 编号的读者也能理解术语、机制与结论。

### 二、历史归档的位置与边界

1. 带有明确时间性的材料（某次长跑结果、某轮发布、某次 CI 阻塞、某次根因定位过程）统一放在 `content/developer/history/`，新路由为 `/developer/history/` 与 `/developer/history/<条目>`，旧 `/history/` 路径通过兼容入口保留；条目 `tags` 至少包含 `历史`，frontmatter 的 `title` 用自然中文并以日期或事件名标识，便于检索。
2. 历史归档**与专题正文分开**：专题页只在「历史变化」「参考资料」中按需链接历史条目，不把历史条目当作唯一证据；历史归档也**不能代替现行技术解释**。
3. 历史条目可以保留轮次编号、日期、Commit 与 Run，但必须写清「当时结论 / 现在是否仍然有效 / 适用版本」，便于后来者判断是否过期。
4. 已被推翻的结论保留必要解释与原始链接，不删除历史；但**现行状态页**只能写当前有效结论，并注明最后核实时间与来源。

### 三、分类与目录命名

1. 面向读者的**类目显示名使用简体中文**，由各分类目录下的 `index.md` 的 `title` 提供；站点左侧目录与目录页读取该标题，不另设英文类目名。
2. **文件路径与 URL 保持稳定**，不因显示名调整而移动目录或改名文件。确需调整时，先检查入站链接，使用 Quartz 的 alias 重定向并验证旧 URL 仍可访问，再更新导航与交叉引用；不得假定文件移动后 Pages 会自动重定向。
3. 分类标签（`tags`）使用中文主题词；技术标识符、API、哈希、命令与路径保持真实拼写。

### 四、双专区发布门禁

1. `/player/` 玩家专区与 `/developer/` 开发者专区必须提供实际内容和导航，不能以空页面、占位页面或仅修改 README 代替。
2. 旧 URL 必须继续返回原页面、有效重定向或明确兼容入口；凡改名页面必须配置 `aliases` 生成重定向，可同时把旧 slug 加入 `scripts/verify-build.mjs` 的 `LEGACY_URLS` 作为长期回归断言，并实际打开验证，不得只依赖构建成功。
3. 正式交付必须完成适用的移动端 Chromium、站内搜索、面包屑、Quartz 构建、CI 与线上 HTTPS 验证；`/player/`、`/developer/` 或关键旧链接任一不可访问时记为 `BLOCKED`。
4. 未审核的 `content/ai-drafts/` 不得进入公开页面、搜索索引或 RSS；AI Summary 只能用于经人工审核的开发者内容。
5. 本地或 CI 的机器检查通过不等于线上发布通过；合并、部署、HTTPS 和关键页面真实访问必须分别记录。

## 原版游戏知识的来源顺序与许可

本站不只记录 MOD 的工程事实，也会解释《反物质维度》原版机制。为避免把传闻、旧攻略或机器翻译当成事实，约定以下来源顺序与许可要求：

### 一、来源优先级

1. **官方源码与游戏内数据**：项目冻结的上游源码（Web）或官方 Android 3.21.0 反编译/资源（Android）是首要依据，优先引用固定 Commit 的具体文件。
2. **项目自有实测与报告**：本项目仓库的 `reports/`、PR、AVD 报告与 `docs/FACTS.md` 用于核对 MOD 行为与已修复结论。
3. **社区 Wiki 与公开资料**：例如 [Antimatter Dimensions Wiki](https://antimatterdimensions.wiki.gg/wiki/Antimatter_Dimensions)，用于理解概念、术语与分类；引用前应尽量用官方源码交叉核对，不能用它替代源码判据。
4. **第三方攻略、视频与转述**：只作线索，不单独作为关键结论的来源。

### 二、原版与 MOD 必须分开写

涉及原版机制的条目，必须明确区分：

- **原版行为**：官方游戏本来就这样（附官方源码或社区 Wiki 来源）；
- **Oreki Edition 修改**：本项目调整了阈值、放宽了条件或增加了自动化（附 MOD 源码/报告）；
- **平台差异**：Android 官方 3.21.0 与 Web 冻结上游并非同一版本，行为可能不同。

不得把 MOD 的缩放数值写成「原版规则」，也不得用原版数值判断 MOD 当前状态。集中对照表见 [原版行为与 Oreki Edition 修改](/player/gameplay/original-vs-mod)。

### 三、版权与署名

- 社区 Wiki 的文本与图像按其版权声明采用 [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) 许可。**原版 Wiki 中文翻译专区（`content/player/original/`）按该许可逐页翻译并署名**；其余专区原则上独立中文撰写，不整页搬运未经核实许可的内容。
- 转载、翻译或改编其受版权保护的文字，必须核实该页面/文件的许可，保留署名与来源链接，注明修改，并按相同或兼容许可共享；图片、图标与第三方素材须单独核实授权，未核实不转载。
- 翻译工程允许机器辅助，但**状态必须如实**：未逐段审校只能标 `TRANSLATED` 或 `STRUCTURE CHECKED`，不能标 `REVIEWED`/「已校对」。
- 仅链接来源不等于取得转载许可；引用少量必要内容时也应说明出处。
- 游戏本体、素材、商标与第三方代码的版权归各自权利人，本站的 CC BY-SA 4.0 授权不覆盖它们。
- **原版 Wiki 中文翻译**统一放在 `content/player/original/` 专区，页面路由为 `/player/original/`，旧 `/original/` 路径通过兼容入口保留。每页必须标注原文标题、URL、修订 ID、页面历史（贡献者入口）、抓取时间与「已修改（翻译）」；翻译规则、署名模板与状态定义见 [docs/translation/POLICY.md](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/translation/POLICY.md)，译名见 [glossary.md](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/translation/glossary.md)。图片与第三方素材不转载。

## 借鉴中文维基百科的补充方针

本节参考中文维基百科的[中立的观点](https://zh.wikipedia.org/wiki/Wikipedia:中立的观点)、[可供查证](https://zh.wikipedia.org/wiki/Wikipedia:可供查證)、[可靠来源](https://zh.wikipedia.org/wiki/Wikipedia:可靠来源)、[非原创研究](https://zh.wikipedia.org/wiki/Wikipedia:非原创研究)和[文明](https://zh.wikipedia.org/wiki/Wikipedia:文明)等方针，**按本项目的工程用途独立改写**，不照抄其条文。本站不是维基百科的一部分，这些是**本知识库自行采纳的编辑规则**，不是维基百科官方对 MOD 的认证。

### 一、中立观点：如实呈现证据，不写宣传稿

在文章中描述功能、缺陷或争议时，使用可核实的事实和有明确来源的判断，不写“完美修复”“绝对稳定”“一定比原版好”等未经证实的结论。若官方基线、Android、Web 或不同候选 APK 的表现相反，应交代各自的版本、时间、运行条件和实际证据。

**中立不等于把所有观点说成一样可信。** 已重现的错误、通过的实测与未经验证的猜测不能占相同比重；按证据质量和问题的重要性组织内容。技术上的负面结果必须保留，不能因为影响项目形象而隐藏。

### 二、可供查证：谁增添关键结论，谁提供来源

关键的数字、兼容性声明、性能比较、成功与失败结论，应在**首次出现的相关句段附近**提供可直接打开的原始链接，尽量使用固定 Commit、具体文件或报告、测试 Run 和版本信息。来源须能真正证明该句结论，不能只在文章末尾堆一串无关链接。

若尚无来源，普通待核问题可明确写“**待补来源**”并列出所需证据；**缺证的核心事实、PASS/FAIL 判定及发布结论不得作为现行确定事实公开**。有来源只是“能核对”，不自动等于“内容正确”；发生冲突时仍应比较上下文与重现实测。

### 三、可靠来源：按问题选用最合适的证据

- **本项目实际行为**：优先引用固定版本的 Android/Web 源码、设备日志、测试报告、构建收据和 CI/CD Run。源码只能证明实现方式，不能单独证明运行成功；PR 描述、模型总结和自述不等于独立实测。
- **第三方软件、标准和平台规则**：优先相应官方文档、标准原文、维护者发布记录，以及经过核实的可靠资料，不凭旧经验猜测当前产品行为。
- **有冲突的来源**：检查时间、版本、环境、来源与被引用结论是否匹配。必要时同时列出，并将未解决部分标为待确认。
- **不作为独立证据的内容**：本 Wiki 其他文章、未经审核的 AI 草稿、无法定位的截图口述、没有原始记录的转述和循环引用。

### 四、禁止无证据综合，但允许有记录的原创工程研究

借鉴“非原创研究”的精神，**不得仅凭几个不相关的 Commit、截图或状态码，综合推导出来源未证明的新结论**。例如“构建通过＋能自动存档”不能被写成“180 分钟内完成游戏”或“正式发布门禁已通过”。

本知识库是工程项目的技术档案，**允许并鼓励原创调试、实验和逆向分析**，前提是提供可以复核的输入、方法、工具或命令、运行环境、原始输出、版本、结果及局限。未实际运行的推测归入“假设/待验证”，不能伪装成实测。

### 五、编辑分歧：围绕证据讨论，不反复覆盖

遇到相反判断时，先在相关 PR 或 Issue 中写明**争议是什么、各自证据是什么、最小核验步骤是什么**，对证据不足的部分暂时标为待确认。修改或撤回已有结论时，在 Git 历史中留下原因和替代证据；重要的被推翻结论应保留历史说明。

反对人身攻击、嘲讽和无来源的权威断言。不要为了赢得讨论而连续覆盖或回滚对方更改。需要尽快修正已确认错误时，可以提交范围明确的小 PR，不必为了流程形式延误事实纠偏。

### 六、版权和署名：借鉴原则，不复制百科文本

规则、技术说明与示意图用自己的语言和材料编写。转载或修改第三方文字、图片、图表、截图与代码前，核实许可、署名和适用范围；**给出链接不自动代表取得转载许可**。需要引用时，尽量使用少量必要引文并说明出处，不整段复制维基百科的方针或条目。

编写 MOD 相关内容时也应尊重原游戏及第三方组件的版权。公开知识库不收录无法授权公开的私有文件、令牌或用户存档。

## README 与公开首页的读者边界

README 和 content/index.md 是面向人类读者的项目门面，不是 Agent 执行规则、内部审计报告或管理员手册。它们应以自然、简洁的中文介绍游戏、Wiki 的阅读价值、玩家专区、开发者专区、贡献方式、来源和版权许可；不得暴露 Kody 配额、CI/部署门禁、HTTPS 设置、历史 PR、Agent 调度、内部台账或详细维护命令。公开开发者首页同样不得把内部授权、任务分派和审查流程作为导航正文。修改后须检查实际构建产物和线上首页，清除新旧信息架构中的内部管理噪声。

首页同时是展示知识魅力的百科门户，而不只是导航中转站。它可以从已审核正文中精选机制、趣闻、成长路线和技术专题；推荐内容必须有真实内链，并随高质量条目滚动更新。文章边界按知识主题和读者任务决定，允许拆分、合并、新建或归档，不以旧文件数量限制重构；调整时须更新站内链接、保存来源与版权，并让旧 URL 到达最合适的新页面。
