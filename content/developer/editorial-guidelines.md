开发者文档最有用的时刻，通常不是“把术语解释完”，而是让人少走一次弯路：知道该从哪个入口读起，知道一段源码能证明什么，也知道什么时候必须把源码和产物、日志或实际运行放在一起看。本页不是 PR 日志的写作模板，而是一套阅读和写作方法。

## 先把问题说成一个动作

“了解 Android 架构”太宽，无法指导阅读；“找到自动购买器从调度到游戏 API 的调用链”就可以。写作前先把目标改成一个可观察的动作，例如：

- 找到一个按钮对应的状态入口，并说明状态在哪里改变；
- 修改一个 Kotlin 适配层后，确认它仍符合旧 DEX 的调用契约；
- 构建 APK 后，判断某个类是否真的进入产物；
- 遇到存档读取失败时，区分编码错误、字段迁移错误和阶段重新计算。

目标越具体，文章越不需要用“背景、意义、总结”填空。读者应该能在开头知道这页要解决什么，读完后知道下一步去哪里验证。

## 四种文章，四种读法

开发者专区的文章可以是教程、操作指南、技术参考或原理说明。它们不是四套固定目录，而是四种读者问题：

| 读者问题                                   | 文章应交付什么                       |
| ------------------------------------------ | ------------------------------------ |
| 我第一次改这里，怎样安全完成一个小任务？   | 有前提、有顺序、有成功判据的入门教程 |
| 我现在要构建、测试或排障，下一步执行什么？ | 命令、输入、预期结果和缩小范围的方法 |
| 这个符号、字段或配置到底是什么意思？       | 稳定入口、语义、约束和版本边界       |
| 代码为什么要这样组织？                     | 模块职责、调用链、数据流和设计取舍   |

例如，[AGP 构建管线](/developer/build/agp)应解释源码如何经过变体、编译、R8、打包和签名成为 APK；[DEX 与 ABI](/developer/reverse-engineering/dex-abi) 应解释寄存器、描述符和适配层怎样共同决定一次调用能否成立。PR 编号只能帮助读者回到证据，不能代替这些解释。

## 先读实现，再读结论

一条技术结论至少要能回答三个问题：它适用于哪个版本，直接证据在哪里，证据还没有证明什么。

阅读 Android 代码时，先从 Kotlin 接管层或明确的入口函数开始，再沿调用链进入反射、静态桥接和游戏 API；需要判断“是否进入 APK”时，再读构建脚本和产物。阅读 Web 代码时，先从启动入口进入游戏循环、机制模块和存档边界，不要用 Android 的类名去猜 JavaScript 模块。

源码证明的是实现方式；构建输出证明的是代码是否进入产物；设备、浏览器和最小样本证明的是某个候选在特定条件下的行为。三者缺一时，文章就应缩小结论，而不是把“看起来合理”写成“已经验证”。

## 让引用帮助读者复核

关键陈述应紧挨可点击的固定来源。优先使用固定 Commit 的具体文件、官方规范和可复现报告；路径和符号要说明它们在论证中扮演的角色，而不是只堆一串链接。来源索引页提供了 [Android/Web 的证据入口](/developer/references/source-index)，逆向专题提供了[从 DEX 到 ABI 的核对方法](/developer/reverse-engineering/)。

不要用以下写法制造“证据感”：只给一个短 SHA、把 CI 绿灯当成功能验证、把历史报告当当前实现、或者列出一串文件却不说明调用关系。行号会随编辑移动；固定提交、相对路径、符号名和适用版本通常更耐用。

## 把复杂内容写得值得读

技术趣味来自真正的矛盾，而不是网络梗。可以解释为什么混淆后的短名字反而迫使我们依赖描述符，为什么寄存器比变量名更接近 DEX 的事实，或者为什么“同一个存档”在解码成功后仍可能因为版本迁移而无法恢复进度。一个准确的比喻、一个最小调用链或一段短源码，往往比十个状态表更能帮助读者建立心智模型。

文章应以自然段为主，表格只用于确实需要并列比较的内容。不要按 R 轮次、日期、PR、Agent 或审查状态组织正文；这些属于历史档案和交接证据。也不要把规则、任务书或验收报告改写成技术文章。读者需要的是当前实现的解释，以及在它发生变化时能够重新验证的方法。

## 发布前的作者自检

作者提交前，应逐段检查：版本和来源是否匹配，路径、命令、数字和术语是否真实，读者能否沿步骤得到可观察结果，源码阅读与实际运行是否被明确区分，旧 URL 和版权信息是否保留。未执行的构建、安装或游戏操作不得写成已通过；不确定的结论应保留为待核实问题。

随后由 Lead 完整阅读最终正文。CI、Kody、链接检查和作者自评都不能代替这次复审；如果实质修改了段落、来源或结论，只需重新复审受影响部分，但未经复审的正文不得合并。
