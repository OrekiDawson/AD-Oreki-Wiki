本站不是项目周报的网页副本。普通玩家希望知道游戏**怎样玩**；开发者希望知道**从哪里开始、哪段代码负责、怎样验证修改、故障发生时该检查什么**。两类读者的问题不同，文章也不能只换一个标题就互相充数。

这里是阅读指南，完整规范以[知识库规则](/wiki-rules)为准。编辑者可参阅仓库中的[不同用途的样板](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/ARTICLE_TEMPLATE.md)，但不要求所有文章有同样的目录。

## 玩家文章：按五种用途写

玩家正在问“是什么”，就写**机制百科**，讲清资源、生产、解锁与重置的因果；第一次要照着点，写**入门教程**，使用真实界面名称、前置条件和可观察结果；遇到推进瓶颈，写标明版本与起点的**分阶段攻略**，解释方案与替代路线，不承诺唯一最优；按钮或存档出问题，写**FAQ/故障指引**，先排除正常限制并保护备份；整理原版资料则是**原版翻译**，遵守原修订、忠实翻译、许可署名及逐段审校。

不同类型不要强制使用相同目录。关键数字、挑战完成次数、研究前置和两端 MOD 规则须核对版本；历史 PR、Kotlin/ABI 和构建 Run 只能作为必要的技术链接，不应成为玩家正文主体。不能用过去一篇 Wiki 的描述去证明另一篇 Wiki 的结论。详见[玩家内容标准](/wiki-rules)和[玩家专区重构台账](https://github.com/OrekiDawson/AD-Oreki-Wiki/blob/main/docs/玩家专区重构台账.md)。

## 开发者文章：先明确要解决的任务

不是所有技术文章都需要从“背景”写到“结论”。开发者专区分为四种常见用途：

| 你想做什么 | 应该找哪种内容 |
| --- | --- |
| 第一次参与项目，完成一项安全的小改动 | **入门教程**：从准备环境到完成一个真实练习 |
| 构建 APK、执行测试、定位故障 | **操作指南**：前置条件、准确命令、预期结果、失败处理 |
| 查询字段、脚本、接口和配置 | **技术参考**：准确符号、定义位置、输入输出和约束 |
| 理解 Kotlin/DEX、调度器或双端设计 | **原理说明**：模块职责、真实调用/数据流、设计取舍 |

一篇架构说明如果只是列出 Android 使用 Kotlin、Web 使用 JavaScript，并附上十个 PR，它仍然没有解释架构。合格的说明应能让开发者找到真正的代码入口，知道状态在哪里变化、数据如何传递、修改后会影响什么。

一篇构建教程如果只有包含占位参数的命令，却没有说明输入从哪里来、在哪个目录运行以及如何判断成功，也不能称为“可执行教程”。**未真正执行过，就诚实写明未执行。**

## 为什么不按开发日志写正文？

一次 R 轮次可能修复过多个不相关模块。把这些记录按日期堆在一起，之后的开发者要先阅读历史才能找到当前实现。

现在的做法是：技术主题只维护当前可证实的解释；历史故障、旧结论和当时的运行环境留在[历史档案](/developer/history/)或源仓报告。主题文章在必要处链接历史案例，不能把旧候选的 PASS 直接拿来证明最新版本。

保留证据与提高可读性并不冲突。源码、Commit、精确接口和原始错误都可以在适当的技术段落出现，只是不应该代替解释。

## 任何实质结论都要有来源

关键技术事实尽量链接到固定 Commit 的具体文件、官方文档或真实测试记录。要区分作者阅读源码、CI 通过、APK 成功安装、实际运行验证和正式发布，它们不是一种证据。

引用原版 Wiki 时，应保留已经真实核对的来源版本；暂时无法访问外站 API，就说明核验尚未完成，不编造 HTTP 200 或修订时间。参考资料列表不能代替正文中的必要出处。

## 编辑、审校与发布

正式新稿或大幅重写先核实原始来源，再按目标读者重写，最后交给**不同于原作者的审校者**独立核查。审校结论至少记录核对了哪些事实和路径、操作步骤有没有执行、仍存在哪些问题。没有通过时记 `EDITORIAL_BLOCKED`，不能用 Kody、CI 或模型自评代替。小幅错字、链接修复只做改动范围内的核对。

暂停按 48 小时或文章数量交付的考核。开发者专区先从首页和最常用的 Android/Web 架构、构建与排障文档逐步重建，保留旧 URL 和原始证据。**目前存在的旧页面，并不因为被列入目录就自动视为已完成审校。**
