“当前状态”不是一条最新消息，而是一条证据链。源码已经合并，只能说明代码进入了某个分支；APK 构建成功，只能说明构建链产出了文件；真正的玩家行为、长时间推进和存档兼容，还要在对应运行环境里单独证明。

## 一条发布链，四种问题

阅读开发状态时，可以把问题分成四层：

1. **实现层**：源码、配置和资源表达了什么设计？入口位于哪个模块？
2. **产物层**：构建系统实际把哪些输入打进 APK 或 Web 部署包？产物身份能否回溯到源码？
3. **行为层**：安装后的游戏是否启动、推进、重置和保存正确？
4. **交付层**：玩家拿到的下载入口是否指向这份产物，旧版本和回滚路径是否仍可辨认？

四层之间是递进关系，不是同义词。产物层通过不能替代行为层；一次冷启动通过也不能替代长时间游戏验收。

## 怎样读 Android Release

Android 发布页至少要能回答四个身份问题：

- 这是稳定版、预发布版还是临时测试包？
- APK 文件名、版本名、版本号和源码提交是什么？
- SHA-256 与签名证书能否确认下载的就是这份文件？
- 发布说明明确写了哪些行为已验证，哪些仍未验证？

“有 APK 资产”不等于“可当稳定版使用”。预发布版本适合用新档和备份存档测试；升级前还要考虑签名、包名和数据目录是否允许覆盖安装。签名机制和 Android 版本兼容性见[APK 签名](/developer/build/apk-signing)。

## 怎样读 Web 部署

Web 版需要区分源码仓库、构建产物和 `oreki.net` 当前响应。一个分支上的源码改动不会自动出现在正式站点；站点能打开也不证明所有阶段、自动化和存档行为都已验证。

排查 Web 问题时，先记录页面部署身份，再确认浏览器站点存储是否属于同一来源。不要用本地 `file://` 直接打开 ES 模块，也不要用刷新页面代替状态迁移。Web 的启动、游戏循环和部署边界见[Web 架构](/developer/architecture/web)。

## “通过”应该说明什么

一个有用的状态描述应当带着对象和范围：

- 构建通过：哪个任务、哪个输入和哪个产物；
- 安装通过：哪个设备/模拟器和哪个 APK；
- 行为通过：哪条操作路径、哪种存档和哪个阶段；
- 发布通过：哪个下载入口、哪个哈希和哪个回滚点。

相反，“CI 绿了”“已发布”“已验证”如果没有对象和边界，就无法帮助下一位开发者复现，也不应被复制到玩家指南里。历史失败和审查记录放在历史/证据层；技术正文只保留理解当前系统所需的因果关系。
