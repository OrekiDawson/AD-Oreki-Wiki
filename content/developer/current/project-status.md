一个游戏版本“能不能交付”，不是由某个绿色标记决定的。源码、构建产物、设备运行和下载渠道分别回答不同问题；只有把它们按同一版本身份串起来，开发者才知道自己究竟证明了什么。Android 的[官方发布文档](https://developer.android.com/studio/publish)也把签名、测试和发布视为不同环节。

## 四层证据

### 实现层：代码表达了什么

先从固定版本的源码和配置确认修复位于哪个模块、由哪个入口调用，以及 Android 和 Web 是否共享同一份机制。Android 的 Kotlin 接管层、绑定表和构建脚本可从[来源索引](/developer/references/source-index)进入；Web 的启动、游戏循环和离线状态见[Web 架构](/developer/architecture/web)。

读到源码只能证明设计已经写入输入，不能证明构建产物包含它，更不能证明玩家一定走到了这条路径。

### 产物层：玩家拿到的文件来自哪里

构建完成后，应把源码版本、构建输入、APK 或 Web 产物和哈希绑定起来。Android 版本还要核对包名、版本号和签名证书；Web 则要核对部署提交与实际响应。详情见[AGP 构建管线](/developer/build/agp)、[APK 签名与升级兼容](/developer/build/apk-signing)和[Web 页面产物完整性](/developer/troubleshooting/web-pages-artifact-integrity)。

“有一个 APK”只说明文件存在；“哈希可追溯”才说明测试对象没有在构建、上传或下载途中悄悄换掉。

### 行为层：安装后真的怎样运行

设备运行需要单独记录环境、存档、操作路径和观察到的状态。启动成功不等于游戏循环正确，能进入某个阶段也不等于后续重置、自动购买器和存档仍然正确。自动化状态机应沿着[自动化停滞排查](/developer/current/known-issues)的状态转移检查，存档问题则见[存档兼容排查](/developer/troubleshooting/save-compatibility)。

Android 与 Web 即使共享数值和阶段概念，也可能在时钟、存储、事件循环或界面边界上产生差异。[双端行为一致性](/developer/architecture/parity)解释如何用同一输入和阶段进行对照，而不是把一端的运行结果直接复制给另一端。

### 交付层：下载入口指向什么

最后确认玩家实际点击的下载或站点入口，确实指向已经核对过的产物。稳定版、预发布版和本地开发包应有清楚的身份；旧版本的兼容和回滚路径也要能辨认。签名正确不能证明玩法完整，CI 通过不能证明真实设备行为，下载页可访问也不能证明所有资源来自同一版本。

## 怎样避免越级推断

| 已有证据 | 可以说明 | 不能说明 |
| --- | --- | --- |
| 固定提交包含某项修复 | 修复进入了构建输入 | 设备已经执行到修复路径 |
| APK 哈希与设备回读一致 | 测试对象就是该 APK | 存档、阶段或终局行为正确 |
| 一次新档走通某个阶段 | 该环境下这条路径可运行 | Android 与 Web 全程等价 |
| CI 或构建任务通过 | 进入下一层验证 | 可以直接作为正式发布 |
| 下载入口可访问 | 读者能够取得文件 | 文件身份、签名和玩法都合格 |

这张表的作用不是给版本贴永久标签，而是提醒维护者每次替换源码、产物或部署提交后重新绑定证据。历史报告可以作为原始资料，但不应代替当前版本的验证。

## 面向读者的排查顺序

遇到“修复没有生效”或“候选能否发布”的问题时，可以按以下顺序缩小范围：

1. 固定源码提交，确认入口、依赖和配置确实包含预期变化。
2. 比较构建产物与设备或站点实际取得的文件，核对哈希、包名、版本和签名。
3. 从全新数据或明确的兼容存档开始，记录启动、推进、重置、保存和回读的状态变化。
4. 将 Android 与 Web 的差异拆成时钟、存储、事件调度和界面四类，不用“看起来一样”代替对照。
5. 只有当测试对象、运行路径和下载入口都能相互指认时，才把结论写成可交付版本。
