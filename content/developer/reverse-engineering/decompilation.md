反编译的终点不是生成一份“看起来像 Kotlin”的文件，而是回答一个更窄、更有用的问题：旧 APK 在某个版本中究竟实现了什么行为，新代码可以依赖哪一条边界。反编译器能把字节码排成近似 Java 的形状，却不会替我们恢复被擦掉的变量名、泛型、协程语义或设计意图。因此，源码恢复必须把工具输出降格为线索，把 DEX 结构、调用路径和运行结果合成可复核的证据。

## 先固定版本，再谈“原始源码”

同一个短类名在不同 APK 中可能指向不同的类型；同一方法的参数也可能因重载或编译器生成代码而改变。调查开始时先记录 APK 的版本、签名摘要、使用的 DEX 文件和反编译工具版本。对 Oreki Edition 的 Android 3.21 基线，[版本绑定文件](https://github.com/OrekiDawson/AD-Oreki-Edition-Android/blob/fb1299a132f134eb4fab009643ee3fc3d6c57edf/baseline/versions/3.21/bindings.json)和[第一方类索引](https://github.com/OrekiDawson/AD-Oreki-Edition-Android/blob/fb1299a132f134eb4fab009643ee3fc3d6c57edf/docs/deobfuscation/data/first-party-3.21-index.csv)只描述该版本的外部边界，不能被当成上游源码的永久映射。

这一步看似保守，却能避免最昂贵的误判：把新版本的结果套回旧版本，随后在 Kotlin 中“修正”一个根本不存在于当前产物的 API。版本信息应与调查笔记和恢复后的测试样本一起保存，而不是只写在文章标题里。

## 证据边界

本文把结论分成三层：DEX、Smali 和描述符直接支持的结构事实；由控制流与调用点支持的行为解释；以及在指定 APK 中实际运行测试确认的工程契约。上文链接的绑定文件和类索引只核对 Android 3.21 的静态映射，不能证明其他版本相同；本文没有把静态阅读当成运行验证，也不把尚未执行的测试写成已通过。

## DEX、Smali 与反编译器各自告诉你什么

DEX 保存类、字段、方法、类型描述符和 Dalvik 字节码。Smali 是更接近这些结构的文本表示，适合检查寄存器、指令和分支；反编译器则把同一结构重新组织成 Java/Kotlin 风格，适合快速浏览控制流。三者不是三个独立的事实源：反编译结果始终可以回到 Smali 和 DEX 验证，尤其要警惕以下情况：

- `p0`、`v0` 等寄存器没有源码变量的语义，必须结合方法签名和赋值路径判断；
- Kotlin 的默认参数、挂起函数、内联函数和数据类会产生源码中看不见的辅助方法或字段；
- 泛型通常在运行时被擦除，反编译器显示的类型参数可能来自签名属性，而不是执行时检查；
- 混淆只改变名称并不等于改变行为，但优化、内联和合成方法会改变原始源码与产物之间的形状。

因此，看到一段可读的伪 Java 代码并不代表已经“恢复源码”。能复核的恢复结果至少应保留方法描述符、关键寄存器流、调用者，以及一条能够解释状态变化的控制流。

## 一条可复核的恢复路径

### 1. 从行为问题开始

先写出待解释的行为，例如“达到条件后为什么显示了自动化按钮”或“保存后哪个字段决定阶段”。问题应包含输入、可观察结果和版本范围。只按类名搜索容易得到大量无关包装器；从一个稳定的 UI 文本、存档字段或调用入口反向追踪，通常更快。

### 2. 用描述符确认边界

方法名和字段名可能被混淆或重复，描述符却明确写出参数和返回类型。先记录形如 `Lpkg/Type;->method(I)Z` 的完整签名，再检查调用点压入了哪些寄存器、返回值在哪里被消费。若两个候选方法只有名字相同而描述符不同，它们就是两个不同的契约。

### 3. 沿寄存器和状态写入追踪

不要只读方法开头。把关键寄存器标成“输入”“临时值”“对象引用”或“返回值”，再追踪它经过的条件分支、字段读取和字段写入。一个布尔返回值只有在观察到调用者如何使用它之后，才可能解释为“已解锁”；它也可能只是“缓存已初始化”。

### 4. 用调用者交叉验证

被调用者说明一段代码能做什么，调用者说明项目把它当成什么。至少找一条正常路径和一条边界路径：例如资源不足、阶段未解锁或读档字段缺失时，返回值是否改变。静态控制流无法覆盖所有运行时状态，但它能告诉我们应当设计哪些最小测试。

### 5. 把结论分层保存

恢复记录应区分三种结论：DEX 中直接可见的结构事实、由控制流和调用点支持的行为解释、已经由运行测试确认的工程契约。前两层不能冒充第三层；一次成功的本地调用也不能自动证明下一版 APK 兼容。

## 为什么新代码要经过 Kotlin 适配层

把混淆类直接散落在业务代码中，等于把一次逆向推断复制成几十个隐形依赖。版本改变时，失败点会从一个解析入口扩散到购买逻辑、UI 和存档处理；如果失败发生在主循环中，玩家看到的可能只是“数字不再增长”。

适配层的职责是把不稳定的类、字段、方法和反射解析集中起来，对外提供语义明确的接口，例如“读取当前阶段”或“请求一次合法重置”。业务代码依赖这些接口，不复制混淆名，也不把反射字符串写进每个调用点。适配层还应在解析失败时记录版本、签名和失败阶段，让排障能够回到真实边界。

这不是把旧 DEX 伪装成一份可编辑的上游源码。它只是把外部 ABI 的不确定性关在一个可替换的房间里：旧入口变化时，优先修改适配层并重新验证契约，而不是让整个项目一起猜。

## 常见的恢复误区

### 把反编译结果当成原始 Kotlin

反编译器可能丢失空安全检查、协程状态机、默认参数和泛型边界。恢复稿可以作为说明行为的伪代码，但引用它时应回到 DEX/Smali 的实际结构；需要在新代码中实现等价行为时，还要补上运行测试。

### 只看名字，不看生命周期

`a()`、`b()` 这类名称没有语义。即使一个字段在某个界面中出现，也不能据此断定它是全局玩家状态。沿着初始化、更新、保存和读取的生命周期观察，通常比继续猜名字有效。

### 用一个样本证明所有版本

绑定资料和恢复结果必须带版本。发生升级时，先比较描述符和调用路径，再决定能否复用旧映射；不要仅因为类名仍然相同就跳过验证。

### 让逆向细节泄漏到业务层

业务层不应知道寄存器编号、混淆类名或反射异常的具体形式。它需要的是稳定的结果和可诊断的错误。这样既便于替换适配实现，也让测试关注游戏机制，而不是某个 APK 的偶然布局。
