排障条目按“现象 → 边界 → 证据”组织：先确认问题发生在源码、构建产物、浏览器运行时还是线上部署，再选择对应专题。

排障的难点通常不是缺少日志，而是日志太容易把人带错方向：一个 `ClassCastException` 可能来自错误的 ABI 绑定，一次“页面不动”可能是调度器在重复跳过同一个状态，读档后回到早期阶段也未必是文件损坏。可靠的排查要把**症状、运行边界、源码路径和最小复现**重新接起来。

## 先画出故障边界

开始前先记录四件事：平台（Android 或 Web）、发布身份、存档是否参与、问题能否在新档复现。它们决定了你应该读哪一层源码：

| 症状                    | 第一处应看的证据                          | 常见误判                         |
| ----------------------- | ----------------------------------------- | -------------------------------- |
| 启动即崩溃              | Android `logcat` 的首个应用异常与启动组件 | 把最后一行 `FATAL` 当成根因      |
| 页面能开但 tick 不推进  | 调度器状态、下一次执行时间和游戏状态门槛  | 反复刷新页面或提高速度           |
| 读档后资源/阶段改变     | 编码、字段迁移、默认值合并和重建顺序      | 直接手改 JSON                    |
| 只有某个 APK 出错       | APK 的源码提交、构建输入和签名身份        | 把源码仓库 `main` 当成已安装产物 |
| Android 与 Web 结果不同 | 两端同一场景的输入、阶段和重置边界        | 用“应该一致”替代行为证据         |

先把问题缩小到一行调用链，再扩大到整套构建或存档。否则每增加一份报告，噪声也会一起增加。

## Android 崩溃定位

对于启动崩溃或点击后崩溃，保留完整的 `logcat`，然后从异常类型向上找第一个属于应用代码的栈帧。系统启动器、Firebase 或 AndroidX 出现在栈顶，并不意味着它们制造了错误；它们常常只是第一个把错误调用触发出来的地方。

如果异常涉及 `ClassCastException`、`NoSuchMethodError`、`NoSuchFieldError` 或 `VerifyError`，优先检查：

1. 调用者看到的 Java/Kotlin 签名是否真的存在于当前 DEX；
2. 混淆类名、泛型签名和 `Continuation` 参数是否被当成了源码签名；
3. 这个类来自新增 Kotlin、冻结 JAR 还是原始 DEX；
4. 构建时打包的输入是否就是设备上安装的 APK。

不要先改调用者的异常处理。若 ABI 已经错位，吞掉异常只会把崩溃变成“按钮无反应”。具体的挂起函数调用链见[协程 ABI 崩溃排查](/developer/troubleshooting/coroutine-abi)，Android 的类来源与产物边界见 [Android 架构](/developer/architecture/android)。

## tick 不推进

调度器停止工作时，先区分：

- **没有调度**：线程或定时器没有再次唤醒；
- **调度了但跳过**：调度器醒来，却因阶段条件、冷却时间或总开关返回；
- **执行了但效果为零**：动作已经调用，游戏状态拒绝购买、重置或结算。

这三个状态在界面上都像“数字不动”，但修复位置完全不同。检查调用链时，沿着“唤醒 → 读取快照 → 判断阶段 → 执行动作 → 写回状态”逐段确认，而不是只看最后一个按钮。

若修改了自动购买器配置，先确认调度器下一次 tick 读取的是哪份状态；某些受托配置会在下一次调度时按合法阶段重新校正。若问题只在切换页面后消失，应把它视为生命周期或状态同步线索，而不是修复结果。相关源码入口可从[双端行为一致性](/developer/architecture/parity)和 [Android 自动化停滞的排查方法](/developer/current/known-issues)继续定位。

## 读档异常

读档排查应保留原文件副本，并按以下顺序缩小范围：

1. 确认文件来自哪一端、哪一版本以及哪次导出；
2. 确认编码层能完整解码，不能解码时不要继续运行迁移；
3. 检查字段迁移和默认值合并是否改变了类型或阶段；
4. 比较“读取前字段”“迁移后对象”和“重建后的游戏状态”三个快照；
5. 用最小脱敏存档复现，再判断是单字段还是整棵状态树的问题。

若导入后像新档，先查存档是否被拒绝后回退到默认状态；若资源少了，查迁移是否把旧字段解释成了新字段，而不是马上认定玩家存档损坏。完整的编码边界、迁移顺序和备份策略见[存档兼容排查](/developer/troubleshooting/save-compatibility)。

## 最小复现应留下什么

一个可迁移的故障报告至少包括：平台与发布身份、最短操作序列、预期与实际状态、脱敏输入、首个异常栈帧或状态转移，以及修复后如何证明问题消失。截图只说明“看到了什么”，不能替代状态和调用路径。

不要把 CI 通过、源码已合并或一次成功启动写成游戏行为已正确。构建、安装、运行、长时间推进和跨端一致性是不同层次的证据。
