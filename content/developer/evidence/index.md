开发者调查最常见的错误不是没有日志，而是让一份证据回答了它没有能力回答的问题。源码可以解释控制流，APK 哈希可以确认测试对象，设备日志可以显示一次行为；它们合在一起才可能支持“这个候选在这个环境中完成了某项验收”。

## 四层证据，各自回答一个问题

### 实现层：代码打算怎样工作

固定 Commit 的 Android/Web 源码、构建脚本、绑定表和测试代码属于实现层。它适合回答入口、调用关系、字段语义和设计约束。例如 Android 的 `GameApi.kt`、`baseline/versions/3.21/bindings.json` 与第一方映射表可以帮助定位混淆接口；它们不能单独证明某个 APK 已包含相同实现，更不能证明真实存档可以走通。

### 产物层：运行时拿到的是什么

APK、DEX、映射文件、构建输出和设备回拉文件属于产物层。它适合回答“源码是否进入了包”“测试设备安装的是不是这份包”“签名和哈希是否一致”。产物层仍不等于行为层：一个能安装的 APK 可能在重置后进入错误状态分支。

### 行为层：这次运行实际发生了什么

设备或浏览器中的日志、截图、状态快照、存档往返和终局字段属于行为层。它必须绑定运行对象、环境、初始数据和时间范围。一次 Android 跑次到达首次现实，可以证明该候选在该环境中推进到那里；只有继续观察到 `isGameEnd=true`，才能支持终局结论。Web 的真实新档记录也只能证明对应 Web 基线，不会自动替 Android 背书。

### 历史层：为什么曾经这样判断

PR、Issue、报告和历史页面属于历史层。它们能解释某个故障怎样被发现、旧修复为何存在以及结论后来怎样变化。历史层不能覆盖当前源码或当前候选的直接证据；引用历史报告时必须同时写清适用的 Commit、APK 或部署版本。

## 一条可复核的调查链

把排障写成下面这条链，而不是把所有链接堆在页面末尾：

**症状 → 固定对象 → 实现入口 → 产物边界 → 最小样本 → 实际行为 → 交叉验证 → 决策。**

例如“现实重置后自动化不再推进”时，先固定 Android 候选和设备环境，再从托管器的阶段判据读到重置前后的字段；随后确认安装包哈希确实对应包含修复的构建；最后用全新存档穿过挑战和现实，观察调度器是否自行恢复，而不是等另一条原版路径偶然把 Break 补回来。这样的链条能区分“判据错误”“产物不是目标版本”和“真实运行尚未覆盖”三种不同结论。

## 证据卡片应记录什么

一条证据不需要把整份日志复制进 Wiki，但至少要能让读者回到原始材料：

- **对象**：源码 Commit、APK 哈希、Web 部署 Commit 或存档样本；
- **环境**：Android API/设备、浏览器、应用数据是否全新，以及关键配置；
- **动作**：做了什么操作，触发了哪个阶段或边界；
- **观察**：实际出现的字段、日志事件、界面或产物；
- **范围**：它证明到哪一步，哪些门禁仍未覆盖；
- **原始链接**：固定源码、报告、Run、Release 或历史归档。

“源码阅读”应写成源码依据，“构建通过”应写成构建依据，“安装成功”应写成安装依据。不要把它们合并成含糊的“已验证”。同样，`NOT RUN` 只应描述尚未执行的具体边界，而不是用来代替故障分析。

## 结论强度不能越级

| 已有材料 | 合理结论 | 不合理外推 |
| --- | --- | --- |
| 源码与单元测试 | 控制流或纯逻辑边界符合预期 | 真实 GUI、存档和终局通过 |
| CI 与构建产物 | 指定提交完成指定检查并产出包 | 玩家路径已经可用 |
| APK 安装、哈希回拉 | 测试对象身份和安装链成立 | 签名升级、节奏和玩法全部成立 |
| 一次设备/浏览器运行 | 某环境、某存档、某候选出现了某行为 | 所有版本、所有存档都兼容 |
| 终局字段为真 | 该运行到达终局判据 | 终局后稳定、渠道发布或双端等价 |
| 正式 Release 与渠道哈希 | 指定资产完成相应交付 | 后续源码改动已经发布 |

当证据冲突时，先检查版本绑定，再选择离问题最近的一层。比如“APK 里有修复但设备仍停滞”，优先查设备回拉哈希和运行日志；“源码说能迁移但存档打不开”，必须补行为层的导入/导出证据。

## 证据的阅读入口

- [来源索引](/developer/references/source-index)：从 Android/Web 源码、构建配置和存档边界找到原始入口；
- [当前项目状态](/developer/current/project-status)：把双端事实转换成“可以继续什么、不能宣称什么”；
- [自动化停滞排查](/developer/current/known-issues)：用重置前后状态和调度分支定位真实故障；
- [发布状态](/developer/current/release-status)：区分公开版本、开发候选、安装证据与发布证据；
- 旧候选和旧报告保留在源码仓库与内部归档中；它们不能冒充当前结论。

原始日志、完整截图和机器报告应留在对应仓库的报告或证据目录；Wiki 负责解释它们如何支持一个技术结论，而不是复制一份难以维护的日志仓库。
