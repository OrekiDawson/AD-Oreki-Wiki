一个 APK 的文件名可以随意复制，构建证据不能。开发者真正需要回答的是：这份 APK 用的是哪一次源码、哪一份 Web 输入、哪套构建工具，以及它是否就是后来验签和发布的那一份文件。

本 MOD 的构建链把这个问题拆成两件事：先为会影响 APK 的输入生成指纹，再把指纹、来源提交和产物摘要写入 provenance。这样，发布故障不必从一个模糊的“构建成功”重新猜起，而可以沿着同一条证据链回到具体输入。

## 提交与产物

源码提交只描述 Git 能看到的内容。完整游戏构建还依赖一些不进入公开仓库的输入，例如官方解码树、游戏 JAR、Web 策略文件和构建工具。Android 工程的 `app/build.gradle.kts` 会从 `local.properties` 解析完整游戏输入目录，并把生成的 Kotlin、资源、Manifest、assets 和 JNI 库接入 `main` source set；这些目录缺失时，提交本身并不能重现完整 APK。

因此，下面两次构建即使使用同一个 Git SHA，也可能不是同一个输入集合：

```text
源码 SHA 相同
├─ 私有游戏 JAR 不同
├─ Web 策略提交不同
├─ 构建工具不同
└─ 生成资源或解码基线不同
```

把“源码版本”误当成“产物版本”，会让验签、回滚和故障复现全部失去指向。

## 输入指纹怎样工作

Android 仓库的 `scripts/release_budget.py` 只把可能改变 APK 的文件纳入指纹：业务源码、构建脚本、基线配置、补丁脚本和工具输入；README、任务记录和普通报告不应改变 APK 指纹。脚本按相对路径和每个文件的 SHA-256 组成整体摘要，同时记录 Python、Java 及本地工具的版本信息。

这一步有两个作用。第一，它能识别“源码没变，但工具变了”的重建；第二，它能拒绝把一次无输入变化的重复构建冒充为新的候选。指纹不是安全签名，也不是对 APK 内容的替代，它只是回答“构建使用了哪些输入”。最终文件仍需单独计算 APK 的 SHA-256。

## 私有输入摘要

候选工作流不会把完整游戏资源提交到公开仓库。它从受保护的 HTTPS 地址下载构建资源包，先检查 URL、访问令牌和预置 SHA-256，再限制压缩包只能展开到允许的目录。工作流还会逐项检查游戏 JAR、官方基线、解码 split 和 Web 单源 JSON 是否存在。

公开日志不需要泄露私有文件路径或令牌，但应留下足够的关联信息：

* Android 源码的精确提交；
* Web 输入的精确提交；
* 私有构建资源包的 SHA-256；
* 游戏 JAR 的 SHA-256；
* 候选 APK 的 SHA-256；
* 版本名、`versionCode`、包名和证书摘要。

缺少私有输入时，正确结果是构建在输入检查处停止，而不是生成一个删减内容的“成功 APK”。这条边界尤其重要：可安装的空壳包只能证明打包工具工作，不能证明完整游戏已经被构建。

## provenance 事实

候选工作流在 APK 生成并通过独立验签后，写入候选目录的 provenance。它把源码 SHA、Web 引用、构建运行编号、游戏 JAR 和资源包摘要、版本身份、证书摘要以及验证报告放在同一个候选上下文中。

可以把它看成一张不可省略的关系图：

```text
Android 源码 SHA ─┐
Web 源码 SHA ─────┼─> 构建输入与候选 Run ─> APK SHA-256
游戏 JAR 摘要 ────┤                          ├─> 签名/版本验证
资源包摘要 ───────┘                          └─> 发布渠道
```

其中任何一条边断开，发布者都无法证明渠道上的文件就是经过验证的候选。渠道可以复制同一个 APK，但不应为每个渠道重新编译一个“内容应该一样”的文件。

## 遇到产物不一致时怎么查

### 文件摘要不同

先比较候选目录、验证作业和发布渠道记录的 APK SHA-256。如果摘要不同，先停止追查签名和游戏行为：当前比较的已经不是同一个文件。确认哪个步骤重新打包或替换了文件后，再回到单一候选重新验证。

### 指纹不同但源码提交相同

读取 provenance 中的工具版本、游戏 JAR 摘要和资源包摘要，再与构建预算账本比较。常见原因是私有输入更新、工具链变化或生成资源没有被固定。不要用“Git diff 为空”推断构建环境没有变化。

### 输入检查失败

先确认构建资源包的摘要是否与仓库变量一致，再确认允许的目录是否完整。若失败发生在资源解压、基线或 Web JSON 检查阶段，修复输入供应链；不要通过删除检查步骤或把缺失资源替换成空目录来让 Gradle 继续。

### 安装或升级失败

产物可追溯不等于产物可升级。确认 APK 摘要一致后，再比较包名、`versionCode`、证书指纹和签名方案；相关的 Android 安装边界见[APK 签名与升级兼容](/developer/build/apk-signing)。

## 开发者应保留什么

修改构建链时，至少保留四类可以互相指向的证据：输入指纹、源码与 Web 引用、APK SHA-256、独立验证结果。日志可以隐藏令牌和私有路径，但不能删除这些关联字段。发布状态页适合告诉读者当前版本身份；本文的 provenance 机制则解释如何证明“当前版本”确实来自那组输入。

这套做法也适用于其他软件项目：把不可公开的输入变成可核对的摘要，把构建产物变成带来源的对象，再让验证和发布只消费同一个对象。构建可重复并不意味着所有环境天然相同，而是意味着差异能够被指出、追踪和复现。
