R8 不只是“把 APK 压小”。它把脱糖、压缩、优化、混淆和 DEX 生成放进 Android 构建的同一条代码处理链；官方文档也提醒，R8 可能移除或改名那些 ProGuard 时代没有被移除的代码，因此反射、JNI 和动态加载入口必须有证据支撑的 keep 规则（[Enable app optimization with R8](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization/)）。

本 MOD 更复杂：APK 中既有官方混淆 DEX，又有以 Kotlin 接管的业务代码和生成绑定。R8 看到的是一次整体优化输入，而不是“只碰新 Kotlin、不碰旧 DEX”的透明滤镜。正式发布默认关闭 R8，独立的 `r8` 变体才用于隔离实验。

## R8 在构建链中的位置

源码和依赖先经过 Java/Kotlin 编译与资源处理，Android Gradle Plugin 为目标变体组织程序类；启用 `isMinifyEnabled = true` 后，R8 在 DEX 生成前读取程序类、库类、keep 规则和入口信息，沿可达性图删除不可达代码、重命名符号并做优化，随后输出 DEX、mapping 和诊断信息。资源压缩是另一条资源侧路径，不能因为代码变小就推断运行速度一定变快。

当前 `app/build.gradle.kts` 的三个关键事实是：`release` 的 `isMinifyEnabled = false`、`isShrinkResources = false`；`r8` 由 `release` 初始化后打开 `isMinifyEnabled`；`proguard-rules.pro` 只在变体真正执行 R8 时发挥作用。因而“文件里有 keep 规则”并不等于稳定包已经启用 R8。

## 调用图的边界

R8 最擅长处理静态可达的调用关系，最容易误伤的是运行时才说出名字的代码。当前 keep 基线按证据分层，而不是用一条 `-keep class ** { *; }` 把优化完全关掉：

- **Kotlin/Smali ABI**：Smali 桥通过类名、方法签名或字段描述符连接生成的 Kotlin。入口一旦改名，编译器不一定报错，运行时才可能出现 `NoSuchMethodError`。
- **GameApi 反射**：`Class.forName`、`getField`、`getMethod` 使用字符串恢复官方混淆类；绑定表中的短名是数据，不是可随意重命名的局部变量。
- **Gson 存档字段**：`player.json` 的键与字段名构成外部格式。保住类却改掉字段名，仍可能让旧档读成默认值。
- **Manifest、JNI 与 WebView**：Manifest 按类名加载组件，JNI 按 native 符号连接，`@JavascriptInterface` 让 Java/Kotlin 成员成为 JavaScript 可见入口。这些都不一定在普通 Kotlin 调用图中出现。
- **生成实现类**：例如 Room 按约定的类名寻找 `_Impl`。类被删掉或重命名，问题会在初始化阶段才露面。

这就是 keep 规则应该描述“为什么这个入口存在”：类名、成员、反射来源和兼容边界都要能追溯到源码、Manifest、存档样本或 DEX 证据。

## 当前实验边界

`r8` 变体不是稳定发布的快捷开关。没有生产密钥时，工程也要求通过 `oreki.allowUnsignedR8Experiment=true` 明确声明未签名实验；任务 `verifyR8SigningDisposition` 会把这种产物标成实验而不是发布包。实验应固定源码 SHA、生成输入、AGP/SDK 工具链和设备条件，并保留 `mapping.txt`、R8 配置与输出摘要。

比较 R8 开关时，至少要同时观察：APK/DEX 大小、类与方法数、构建耗时、冷启动、游戏 tick/UI、内存、存档保存/重载、阶段门禁、自动购买器和真实结算。只测出“文件更小”不能证明 ABI 仍兼容；只通过单元测试也不能证明反射和混淆 DEX 的运行时入口完整。

Android 官方建议在大型应用中渐进采用优化，例如先关闭混淆、分区域启用，再逐步收紧 keep 规则（[Adopt optimizations incrementally](https://developer.android.com/topic/performance/app-optimization/adopt-optimizations-incrementally)）。对本项目，这意味着先保护已知 ABI 和存档边界，再用真实失败缩小规则，而不是一次性把整包改成黑盒。

## 失败如何缩小范围

看到 R8 构建失败时，先按现象定位：

1. **缺失引用/警告**：确认类确实来自输入还是只存在于设备侧可选 API；不要用全局 `-dontwarn` 把未知问题静音。
2. **启动即崩**：优先检查 Manifest、初始化器、生成实现类和 JNI；这些入口在应用启动前就可能触发。
3. **进入某功能才崩**：检查 GameApi 的反射字符串、生成绑定和对应 keep 成员，再用 mapping 还原堆栈。
4. **存档读出异常**：比较旧档键名与 R8 后字段名，确认 `Signature` 等泛型属性是否保留，并验证旧档写回而不只是“能打开”。
5. **运行正常但结算/自动化异常**：检查被优化的桥接方法、Continuation 和状态字段；把机制错误与 APK 安装问题分开验证。

`mapping.txt` 是把混淆堆栈带回源码语义的地图，不是兼容性的证明。每次实验都应把 mapping、输入和 APK 摘要绑定起来，否则今天还原出的堆栈可能对应昨天的包。

## 可迁移的设计经验

R8 的真正难点不是记住某条 keep 语法，而是识别系统边界：编译器看不见的入口必须显式建模；外部格式的字段名必须当作 API；实验变体与稳定变体必须有不同的发布权限；优化收益必须和运行证据一起衡量。这个思路同样适用于插件系统、序列化框架和任何把“名字”当数据传递的程序。
