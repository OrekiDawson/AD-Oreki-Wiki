R8 的工作不是简单地“删掉没用的类”。它在 Android 构建中接过 Java/Kotlin 编译产物，结合程序类、库类、入口和 keep 规则，完成压缩、优化、重命名与 DEX 输出。对普通 Kotlin 应用，调用图已经能描述大部分入口；对本 MOD，Smali 桥、官方混淆 DEX、Gson 存档和 WebView/JNI 会把“名字”变成运行时数据。R8 看不见这些证据时，最危险的结果往往不是构建失败，而是 APK 启动后才失败。

本文依据 Android 仓库固定基线 [`9d8fc46`](https://github.com/OrekiDawson/AD-Oreki-Edition-Android/tree/9d8fc46ce99279720b5b3068027bb76bceb35756)，重点对照 `app/build.gradle.kts`（源码定位：OrekiDawson/AD-Oreki-Edition-Android@9d8fc46ce99279720b5b3068027bb76bceb35756/app/build.gradle.kts） 和 `app/proguard-rules.pro`（源码定位：OrekiDawson/AD-Oreki-Edition-Android@9d8fc46ce99279720b5b3068027bb76bceb35756/app/proguard-rules.pro）。

## R8 在生命周期中的位置

一条 `r8` 变体的关键路径是：

```text
Java/Kotlin 源码 + 生成绑定 + 官方/转换后的程序类
        ↓ kotlinc/javac 与资源处理
AGP 为 r8 变体收集 program classes、library classes、Manifest 和规则
        ↓ R8：可达性分析、压缩、优化、重命名、DEX 输出
classes*.dex + mapping.txt + APK 资源
        ↓ packageR8 → verifyR8SigningDisposition
实验 APK（有签名才可按发布身份继续；未签名只能是实验）
```

在当前 `app/build.gradle.kts` 中，`release` 明确设置 `isMinifyEnabled = false`，而 `r8` 通过 `initWith(release)` 继承 Release 配置后再设置 `isMinifyEnabled = true`。这项分层是故意的：正式 Release 的行为基线不因一次 R8 实验而改变，实验也必须有自己的签名处置证据。

`isShrinkResources` 属于资源侧压缩，当前 Release 同样关闭。代码变小、资源变少和运行更快是三个不同命题；R8 通过不代表资源引用、启动行为或游戏节奏已经验证。

## 全局 keep 的问题

`app/proguard-rules.pro` 没有使用 `-keep class ** { *; }` 把优化关掉，而是按入口来源分层。这样做的取舍是：规则更难维护，却能让真正静态可达的代码继续压缩，同时把动态边界写成可审计的证据。

### Kotlin/Smali 桥是二进制接口

规则保留 `kajfosz.antimatterdimensions.oreki.**`，以及 `OrekiAuto`、`OrekiTrace`、`OrekiChallengeAuto`、`OrekiInstantChallenge`、`OrekiSpeed` 和 `OrekiEcContinuation` 等顶层桥类。原因不在于这些类“比较重要”，而在于 `scripts/payload/smali/kajfosz/antimatterdimensions/oreki/` 中的 Smali 描述符按类名、方法签名和字段连接到它们。R8 把一个类改名，Kotlin 编译器不会替已经存在的 Smali 重新检查；错误会延迟到运行时。

### GameApi 的字符串不是普通字符串

GameApi 通过 `Class.forName`、`getField` 和 `getMethod` 访问官方混淆类；生成的 `build/kt/generated/OrekiBaselineBindings.kt` 又保存 3.20→3.21 的映射，例如 `bq0→iq0`、`u41→d51`。因此规则还保留 GameApi 涉及的游戏包，以及绑定表中的短名类。修改映射时，必须同时核对生成绑定、目标 DEX 和调用点；只改 Kotlin 常量而不改真实类名，属于把编译期数据当成实现细节。

### Gson 存档是外部格式

`Player` 树被 Gson 写入 `player.json`。规则中的大量 `-keepclassmembers ... { <fields>; }`不是为了让代码好看，而是为了保住存档键对应的字段名。类还在、字段却被重命名，同样会让旧存档读成默认值或丢失一部分进度。修改 Player 数据类、嵌套状态或序列化注解时，应把“旧档导入—读取—写回—再次读取”当成兼容性测试，而不是只测冷启动。

### 运行时入口

Manifest 按字符串加载 `App`、`MainActivity`、初始化器、Firebase/WorkManager 组件；JNI 通过 native 方法连接；`@JavascriptInterface` 把 Java/Kotlin 方法暴露给 WebView；Room 则按约定寻找 `WorkDatabase_Impl`。这些入口未必出现在 Kotlin 的普通调用图中，所以规则分别保留 Manifest 中真实存在的类、带 `@JavascriptInterface` 的方法、native 方法和 Room 生成实现类。

## 修改 R8 规则的正确顺序

遇到一个需要保留的符号，先回答“谁用名字找到它”，再写规则：

1. 在 `app/src/main/kotlin`、`build/kt/generated`、Smali、Manifest、JNI 声明和 WebView 注解中定位调用方。
2. 判断入口是类名、成员名、字段名、签名属性还是生成类约定；不要先扩大到整个包。
3. 用最小的 `-keep`、`-keepclassmembers` 或 `-keepattributes`表达证据。当前基线保留 `Signature`、注解、内部类和封闭方法属性，是为了支持反射、泛型和运行时注解。
4. 若看到 missing reference，先证明它来自哪一侧。当前规则只对已核对的官方 DEX 悬空引用使用精确 `-dontwarn`，不以全局 `-dontwarn` 把未知类静音。
5. 先在 `r8` 变体构建，再用 mapping 还原堆栈，最后做运行和存档验证。通过构建不等于规则正确。

## 怎样运行一个隔离实验

从 Android 仓库根目录执行：

```bash
./gradlew :app:assembleR8 --no-daemon --console=plain
```

如果本机没有 `keys/oreki.jks`，`verifyR8SigningDisposition` 会拒绝继续，除非在 `local.properties` 中明确设置：

```properties
oreki.allowUnsignedR8Experiment=true
```

这个开关只说明“允许未签名实验”，不会把实验包变成可发布包。正式签名路径仍需要 `keys/oreki.jks` 和 `OREKI_KS_PASS`。实验应记录固定源码 Commit、输入阶段、AGP/SDK、规则文件、APK 摘要和 `mapping.txt`；否则两次混淆结果无法可靠比较。

## 从症状反推边界

**R8 阶段缺失引用**：先确认缺失类来自程序类、Android SDK、可选设备 API 还是官方 DEX 的既有悬空引用。只对有证据的类别添加精确 `-dontwarn`；把所有警告吞掉会掩盖真正的转换错误。

**启动即崩**：优先查 Manifest 组件、AndroidX 初始化器、Firebase/WorkManager 注册类、Room `_Impl` 和 JNI。它们通常在玩家还没有点进游戏前就被加载。

**进入某个机制才崩**：查 GameApi 的反射字符串、生成绑定和对应类/成员的 keep 范围。用 `mapping.txt` 把混淆堆栈映射回源码，再确认调用方使用的是哪个固定版本。

**旧档能打开但数值丢失**：比较 `player.json` 键名与 R8 前后的字段名，检查 `Signature` 和 Gson 相关成员是否保留；“首页能显示”不能替代完整存档回归。

**自动化或结算变慢/不动**：检查桥接方法、Continuation、状态字段是否被优化或重命名，并把运行时逻辑问题与 APK 安装问题分开。R8 只负责代码处理，不负责证明调度器的数学结果。

## 可迁移的经验

R8 的核心知识不是背诵 keep 语法，而是把所有“编译器看不见的入口”显式建模：字符串是 API，存档字段是格式，Manifest 是注册表，JNI 和 WebView 是跨语言调用，生成类名是框架协议。每新增一条规则，都应同时留下入口来源、最小保留范围和验证方式；这套方法同样适用于插件、反射序列化和任何动态加载系统。
