自动购买器的开关不是一个孤立的布尔值。至少有玩家当前设置、原版自动购买器总开关、MOD 调度器开关、阶段策略目标和一次动作的执行资格。真正需要回答的问题不是“现在是开还是关”，而是：**这个值由谁决定，谁有权写，玩家刚刚介入后谁必须让路。**

本文只讨论配置的写入边界；任务如何排队见[调度器状态机](/developer/architecture/scheduler-state-machine)。先澄清一个容易误读的地方：当前 Android 源码中没有名为 OrekiPlayerIntent 或 OrekiManagedAutobuyerAuthority 的独立类。相关职责分布在 OrekiAutomationScheduler、OrekiStageAuto、设置监听器和 GameApi 中，不能把概念名称当成实际模块。

## 三种决定

把自动化写回拆成三个决定会更清楚：

1. **玩家决定是否让路。** 玩家关闭原版总开关时，MOD 不应把它当作“下一帧自动恢复”的信号。
2. **策略决定目标值。** 阶段模块可以提出“希望某项自动器开启、关闭或保持”的目标，但目标不是写入授权。
3. **调度器决定本次能否执行。** MOD 开关、原版总开关、全局间隔、同帧名额、失败冷却和任务预约共同决定是否可以触碰原版入口。

这三步不能合并成一个 enabled。策略目标可以是开启，执行资格却可能因玩家刚关闭总开关而为假；执行资格为真，也不代表每一项配置都归 MOD 管理。

## Android 的真实边界

OrekiAutomationScheduler 持久化并读取 oreki.automation.enabled、oreki.automation.intervalSec 和 oreki.automation.strictGlobal。调度器关闭时，allow() 直接拒绝，并清理待执行预约、失败冷却和 no-op 状态；最近一次真动作的时间戳仍保留，重新开启不能借机绕过动作间隔。

allow() 还会通过反射读取原版 Player 的自动购买器总开关。读取失败时按关闭处理，这是一个重要的安全取舍：自动购买会消耗资源，停摆比在不确定时越权写入更可恢复。通过闸门后，调用方仍必须沿原版入口执行，并用 noteActed、noteNoop 或 noteFail 回报结果。

OrekiStageAuto 负责把阶段策略接到这些闸门上。它可以在当前阶段设置紧迫任务，改变尝试顺序；它不能给紧迫任务额外名额，也不能绕过调度器直接连续购买。配置同步、真实购买和重置应分别看作不同动作，不能用一次“总开关恢复”掩盖三者的差异。

## 玩家关闭后的含义

玩家关闭原版总开关，至少说明当前动作不应由 MOD 继续推动。它不自动说明玩家想永久修改所有单项配置，也不自动说明稍后可以恢复。实现玩家让路时，应保留“当前原版值”和“策略目标”两个概念，并在下一次策略周期重新判断，而不是在每帧看到差异就写回。

| 观察 | 可以推断 | 不能推断 |
| --- | --- | --- |
| 原版总开关关闭 | 当前应停止 MOD 受管动作 | 可以立即重新打开 |
| MOD 调度器关闭 | allow() 不应放行动作 | 旧预约可以稍后自动执行 |
| 目标与实际值不同 | 存在待判断的配置差异 | 当前拥有写入权 |
| 原版入口返回无变化 | 本次是 no-op | 动作已成功推进 |

这里的核心不是记住更多布尔值，而是避免把“目标不同”误当成“权限存在”。

## 延迟与幂等

配置同步不应在每个循环帧发现差异后立即写入。更安全的做法是：观察到差异时登记一次待处理状态，重复观察不刷新登记时间；到达策略周期后再消费一次，并在总开关、玩家让路或阶段变化时清除旧登记。写入入口还应是幂等的：实际值已经等于目标时不重复写，不要把无变化调用计为成功动作。

这类延迟状态不能与全局动作节拍混为一谈。设置同步可能只是改变开关或间隔，购买和重置则会消耗资源；它们的成功判据、恢复策略和读档影响不同。调度器状态机页负责公共动作节拍，本页只说明谁能提出写入和何时必须让路。

## Web 的对应边界

Web 的 OrekiSmartExecutor 把策略、观察和执行分开：阶段模块先通过 observe() 报告本轮动作摘要，执行器在模块空闲时才选择候选 verb；玩家点击相关界面后，策略层会设置手动让路窗口。执行器不直接修改 player 字段，而是调用已注册的原版或阶段入口。

这与 Android 的类名并不相同，但契约相同：策略提出目标，执行层验证资格，原版入口完成状态改变，下一轮重新观察。不能因为两端都有“自动化开关”就假定它们的持久化键、事件顺序或写入方法相同。

## 修改自动化时的检查顺序

新增一项受管配置时，先回答：

1. 它是玩家设置、策略目标，还是执行记账？
2. 哪个组件是真正的写入者，哪个组件只读？
3. 玩家手动介入和 MOD 关闭时，待处理状态如何清理？
4. 成功、无变化和失败分别怎样被观察？
5. 保存和重载后，实际值与策略目标是否仍可区分？

如果答案只能写成“发现关闭就重新打开”，边界还没有定义好。尤其不要在 OrekiStageAuto 中复制一套绕过 allow() 的快捷逻辑，也不要直接写 player 字段来制造“已解锁”。

固定源码定位：Android OrekiAutomationScheduler.kt、OrekiStageAuto.kt、GameApi.kt，以及 Web oreki-smart-executor.js；对应资料版本为 Android 1ec0c9cadd803f8f4e0e1c0e743c3557ab15a545、Web e1c93caa758de6c39cf814582123d4a35319eb25。
