自动化最危险的故障不是“程序没有运行”，而是程序一直运行，却反复尝试一个不会改变状态的动作。要读懂这种问题，不能只看线程是否有心跳；要看一次动作从快照、候选、闸门到结果回报，是否完成了一个闭环。

本文把 Android 与 Web 的实现放到同一张状态图里，专门解释动作调度、重置和进度死锁。自动购买器配置的玩家所有权见[自动化所有权](/developer/architecture/automation-ownership)，大数阈值见[数值模型](/developer/architecture/numeric-model)。

## 一次调度周期

两端虽然入口名称不同，但可观察的生命周期都可以写成：

    读取状态 → 产生候选 → 通过阶段与资源门 → 执行动作
        ↑                                      ↓
        └──────── 重置或状态变化后重新读取 ← 结果分类

候选只是“现在值得尝试”，不是许可。结果至少要分成四类：

- acted：游戏状态确实改变。
- no-op：调用合法，但当前没有可改变的东西。
- fail：调用或适配层明确失败。
- blocked：在执行前被阶段、挑战、资源或开关挡住。

把 no-op 当成成功会制造假进度；把 blocked 当成异常会把正常等待变成错误报警；把 fail 当成资源不足则会掩盖入口或调用链问题。

## Android 的单动作节拍

Android 的自动化入口是 OrekiStageAuto.onAutoBuyerTick()。每次进入先调用 OrekiAutomationScheduler.beginFrame()，再按阶段尝试现实、永恒、献祭、批量购买、无限升级、坍缩间隔和维度购买等任务。真实购买或重置动作要经过：

    allow(taskId) → GameApi / 原版入口 → noteActed / noteNoop / noteFail

allow() 依次检查 MOD 开关、原版自动购买器总开关、任务是否注册、本帧名额、失败冷却、no-op 静默窗、全局间隔和任务预约。beginFrame() 建立同帧记账边界；noteActed() 推进全局节拍并占用本帧唯一的真动作名额；noteNoop() 不推进节拍，只给该任务设置重试静默；noteFail() 设置独立的失败冷却。

调度器的任务 ID 按索引保存时间戳和统计数据，因此新增任务应追加而不是重排旧 ID。阶段紧迫任务可以改变“先问谁”的顺序，但不绕过 allow()，也不获得额外动作名额。这样既能处理 ID 购买被前置任务长期饿死的问题，又不把全局节拍重新拆成多套。

## Web 的策略与执行

Web 的 gameLoop() 先推进原版生产和自动购买器，再把阶段模块的动作摘要交给 OrekiSmartExecutor。执行器维护候选动作、每项的最近执行时间、no-op 冷却、全局间隔、手动让路窗口和阻塞说明；它不会另造一份资源或直接给 player 字段赋值。

Web 的关键边界是“阶段模块先做，执行层只在模块本轮没有动作时补位”。observe(source, result) 用阶段模块返回的摘要清除对应的空闲计数；连续空闲达到门槛后，执行器才从策略允许的 verb 中选择候选。若玩家在界面上执行相关操作，手动让路窗口会暂时抑制同一目标的自动动作。原版自动购买器和阶段模块自身的合法动作不应被执行器重复调用。

因此，修购买顺序要先看策略模块，修节拍要看执行器，修重置语义要沿着原版 bigCrunch、eternity 或 reality 入口追到底。不要在执行层写另一份“资源够了就买”的逻辑，否则同一笔资源会出现两个竞争者。

## 重置是状态转移

合法重置不是把计数器改成目标值，而是一条由游戏核心完成的转移：

1. 当前状态满足阶段与资源条件。
2. 调度器调用原版或适配层的重置入口。
3. 游戏核心清理当前层资源、发放奖励并更新历史记录。
4. 下一轮重新读取状态，进入恢复或继续积累。

无限点数、永恒点数和当前挑战资源可能在重置后改变或清零；完成次数、升级和阶段解锁则是历史证据。决策状态机必须把这两类字段分开，否则现实重置后会重新走“首次完成”分支，或在尚未结算时误判为已经完成。

## 等待、饥饿与死锁

资源尚未达到门槛，只要资源继续增长，就是正常等待。饥饿是系统整体在推进，但某个低优先级任务一直拿不到名额；死锁则是当前状态没有任何可达后继。

| 现象 | 优先检查 |
| --- | --- |
| 同一候选反复出现，资源也不变 | 快照来源和阶段判据 |
| 某任务连续 no-op，其他任务也不执行 | 空操作是否错误占用全局节拍 |
| 手动操作能继续，自动化不断跳过 | 开关、挑战和阶段门 |
| 重置后回到首次进度分支 | 是否把当前资源当成历史证据 |
| 记录为成功但资源和次数都不变 | 成功判据是否只看函数调用 |

排查应保存一个最小快照：阶段、候选任务、重置历史、相关资源、开关、上次动作和结果。先确认动作前后状态是否真的变化，再检查调度节拍；把“线程仍在运行”当作成功，会让死锁隐藏得更久。

## 回归场景

比起无边界地运行很久，更有价值的场景是从一个固定阶段存档跨过一次会清空当前层资源的重置，然后检查：当前资源按规则清理，历史进度仍在，调度器进入恢复分支，资源不足时等待，满足条件后才发出下一次合法动作。另一个场景是让前置任务连续成功，确认紧迫任务仍能获得一次尝试，同时所有动作继续经过同一闸门。

固定源码定位：Android OrekiStageAuto.kt、OrekiAutomationScheduler.kt、GameApi.kt，以及 Web game.js、oreki-smart-executor.js；对应资料版本为 Android 1ec0c9cadd803f8f4e0e1c0e743c3557ab15a545、Web e1c93caa758de6c39cf814582123d4a35319eb25。
