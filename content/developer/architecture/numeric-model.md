反物质维度很早就会越过普通双精度数字适合工作的范围。接近 `1.80e308` 时继续相乘可能得到 `Infinity`，更早的时候则会先出现有效位丢失：两个在游戏规则上不同的资源，被普通 `Number` 或 `double` 舍入成同一个近似值。于是大数库不是显示层的装饰，而是购买、阈值、结算和存档的一部分。

两端都把数值拆成“尾数 + 数量级”，但 Web `Decimal` 和 Android `BigDouble` 是不同的类型。本文解释共同数学结构与端侧边界，不把两端的字段或序列化格式假定为可直接互换。

## 尾数与指数

一个正的非零数可以近似写成：

```text
value = mantissa × 10^exponent
```

规范化会把尾数调整到约定范围，零、负数、`NaN`、无穷大和最大指数则另行处理。规范化不是排版步骤：后续比较、加减和显示都依赖它保持一致。

普通浮点数的两个限制必须分开看：指数有限，所以会溢出；有效位有限，所以在数量级很大时，小增量可能被吞掉。只把显示改成科学记数法并不能解决任一问题。

## Web 的 `Decimal`

Web 端在 `modules/break_infinity.js` 中提供 `Decimal`，货币层的 `DecimalCurrency` 继续以该对象保存资源。购买和门槛代码应使用 `plus`、`times`、`gte`、`log10` 等 Decimal 操作；一旦先调用 `toNumber()`，后面的逻辑就回到了普通浮点数的范围和精度。

乘法的核心可写成：

```text
(2.5 × 10^400) × (4 × 10^3)
= 10 × 10^403
→ 1 × 10^404
```

最后一步是归一化。加法更棘手：必须先对齐指数；若两者数量级差距很大，小数一方可能在当前精度内没有可见贡献。阈值判断常常只需比较数量级和尾数，不应先构造一个会溢出的 `Number`。

## Android 的 `BigDouble`

Android 3.21 基线中的 `BigDouble` 同样保存 `mantissa` 和 `exponent`，并提供比较、序列化和运算语义。Kotlin 适配层的 `GameApi` 以宿主对象为边界，提供大数比较、乘法、减法及资源读取；`compareBigDoubles()` 会选择 `BigDouble` 对 `BigDouble` 的比较，而不是把双方粗暴转成 `double`。

这一区别很关键：反编译结果里看到两个 `double` 字段，不表示整个对象可以替换成一个 `double`。对象的规范化、特殊值、比较重载和写回方式同样是数值契约的一部分。适配层如果只保留一个近似值，最先出问题的通常是高阶段门槛，而不是普通数字显示。

## 跨端比较什么

比较 Web 与 Android 时，不要拿 JSON 文本或界面格式直接比。至少要分别确认：

1. 同一输入在两端的数量级和符号。
2. 对同一阈值的比较结果。
3. 购买或重置后的资源变化。
4. 保存、重新载入后的数值与阶段状态。

即使两端都显示 `e308`，尾数舍入不同也可能让一个端先满足门槛；反过来，显示格式不同但阈值和结算一致，问题可能只在 notation 层。保存格式也不一定相同：某端可能用字符串，另一端可能用对象或尾数/指数字段，必须交给本端解析器处理。

## 数值错误如何穿透到玩法

一个购买按钮不出现，可能是资源在适配层被转成了 `Infinity` 或零；一次结算没有发生，可能是收益比较在转数值时失去精度；读档回到默认值，则可能是序列化器没有保留大数对象。不要先降低门槛来“证明”流程正常，那会把表示错误掩盖成平衡错误。

定位时沿着数值生命周期走：来源是原版对象还是存档字段，进入适配层后仍否保持大数类型，比较调用的是哪一个重载，错误出现在归一化、阈值、序列化还是显示。每一步都要保留端侧的真实类型和数量级。

## 回归样例

大数实现至少要覆盖三组样例：

- 运算不变量：乘以 `1`、除以自身、比较传递性，以及零、负数、特殊值。
- 边界样例：`1e308` 附近、指数进位点、尾数刚跨过阈值的两个值。
- 跨端往返：同一尾数/指数输入，比较阈值结果，再执行合法保存和重新载入。

普通 `1e10` 样例只能证明普通数值路径工作，证明不了大数库最重要的边界。具体测试命令与构建环境不在本文虚构；若当前仓库没有可运行的端侧测试入口，应在工程资料中另行补齐，而不是把命令写进文章当作已验证事实。
