在《反物质维度》里，$1.80 \times 10^{308}$ 不是遥远的理论例子，而是玩家很快就会撞上的第一面“普通数字天花板”。如果把这样的值交给 JavaScript `Number` 或 Java `double`，程序不会自动变成能处理无限大的计算器：它会溢出、失去有效位，或者把两个本应不同的状态压成同一个近似值。

因此游戏把大数拆成两个更容易控制的部分：**尾数**和**指数**。这不是为了让数字看起来更长，而是把“数量级”和“数量级以内的比例”分开保存，使比较、乘除和显示都能在远超普通浮点范围的区间工作。

## 为什么不能直接使用普通浮点数

IEEE 754 双精度浮点数的指数范围和有效位数都有限。它适合普通业务金额，却不适合一个会把资源推到 $e^{100000}$ 以上的放置游戏：

- 接近 $10^{308}$ 时，继续相乘可能得到 `Infinity`；
- 两个相邻可见数字之间的间隔会越来越大，小增量可能完全消失；
- 把大数转换成普通 `Number` 后，比较结果可能与游戏的阈值语义不一致；
- 序列化时若先转成普通数字，读档得到的可能是溢出值，而不是原来的数量级。

Web 原版在普通数字达到上限后使用 `break_infinity.js` 的 `Decimal`。Android 官方 APK 的反编译证据则显示宿主运行时使用 `BigDouble`；两者都采用尾数/指数思想，但它们不是同一个类，也不能把一端的对象直接当成另一端的值。

## 两端的实际表示

### Web：`Decimal` 的规范化尾数与指数

Web 的 `modules/break_infinity.js`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/modules/break_infinity.js；具体文件证据留在内部核验记录） 在构造 `Decimal` 时维护 `mantissa` 与 `exponent`。规范化后的值可以近似理解为：

```text
value = mantissa × 10^exponent
1 ≤ |mantissa| < 10        （非零正常值）
```

零、负数、`NaN` 和无穷大需要单独处理。源码还设置了普通数字指数范围、最大指数和有效位数等边界；这些常量不是“显示格式”，而是运算实现的一部分。

游戏的货币层在 `src/core/currency.js`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/src/core/currency.js；具体文件证据留在内部核验记录） 中通过 `DecimalCurrency` 暴露 `mantissa`、`exponent` 和 Decimal 运算对象。上层购买、阈值和生产代码应使用 `plus`、`times`、`gte`、`log10` 等 Decimal 操作，而不是把 `.toNumber()` 后再计算。

### Android：宿主 DEX 的 `BigDouble`

Android 3.21 基线的 `BigDouble.smali`（源码定位：OrekiDawson/AD-Oreki-Edition-Android@1ec0c9cadd803f8f4e0e1c0e743c3557ab15a545/reports/r50/apk_a13/smali/kajfosz/antimatterdimensions/BigDouble.smali；具体文件证据留在内部核验记录） 明确声明了 `mantissa:D` 与 `exponent:D` 两个实例字段，并保留 `Comparable<BigDouble>` 与 `Serializable` 的类型信息。它还包含最大指数、最小指数、归一化容差和最大有效位数等常量。

这给源码恢复一个重要提示：反编译器显示两个 `double` 字段，并不意味着游戏逻辑可以把整个对象替换成一个 `double`。比较、归一化、序列化和可变性都属于 `BigDouble` 的语义。Android Kotlin 适配层应通过 [DEX 与 ABI](/developer/reverse-engineering/dex-abi) 记录的类名、描述符和调用边界使用宿主对象，而不是复制一套“看起来相似”的数字类。

## 运算为什么要先看指数

尾数/指数表示让常见操作有清楚的算法路径。

### 比较

对两个正数，通常先比较指数；指数不同，数量级大的值更大。指数相同时再比较尾数。符号、零、`NaN` 和无穷大必须在这条捷径之前处理。这样比较 $1.2 \times 10^{100000}$ 与 $9.9 \times 10^{99999}$ 不需要把它们还原成普通浮点数。

### 乘除

乘法可以先乘尾数、再相加指数；除法则相反。得到的新尾数可能超出规范区间，因此还要重新归一化：

```text
(2.5 × 10^400) × (4 × 10^3)
= 10 × 10^403
→ 1 × 10^404
```

最后一步不是排版，而是保证后续比较和显示都能假设尾数处在约定范围内。

### 加减

加法更棘手，因为两个数必须先对齐指数。若指数差距很大，小数的一方可能在当前精度下没有可见贡献；若不处理这个边界，程序会在“数学上应该增加、机器上却完全不变”的地方产生误判。`break_infinity.js` 的加法实现因此不能简单写成两个普通 `double` 相加。

### 对数与阈值

游戏经常使用数量级作为门槛。对规范化的正数，`log10(value)` 可以近似由指数和尾数的对数组合得到，而不必先构造一个会溢出的普通数字。源码中的 `log10`、`exponent`、`mantissa` 既是运算 API，也应被视为跨端对照时的事实入口。

## 跨端一致性不等于字段相同

Web 的 `Decimal` 与 Android 的 `BigDouble` 都能表达“尾数 × 十的指数次方”，但仍有四类差异需要显式处理：

1. **归一化约定。** 尾数允许的区间、负零处理和边界修正可能不同。
2. **精度与舍入。** 尾数使用双精度时，指数相同的小数运算仍会丢有效位；不能用格式化文本判断是否精确相等。
3. **特殊值。** 零、负数、`NaN`、`Infinity` 和最大值的排序与序列化必须逐项对照。
4. **保存格式。** JSON 中保存的字段可能是字符串、对象或尾数/指数组合；导入时必须经过本端解析器和迁移逻辑，不能靠两个 JSON “长得像”来互通。

实际比较时，建议保留以下检查点，而不是只截一张 UI 图：

```text
本端原始值
→ 尾数/指数或等价的数量级
→ 阈值比较结果
→ 结算后的资源与阶段
→ 保存并重新读取后的值
```

如果显示都为 $e^{308}$ 但只有一端解锁，优先比较阈值判断前的指数、尾数和舍入；如果数值显示不同但阈值、结算和读回值一致，问题可能只是 notation 层，而不是玩法分叉。

## 为什么“大数错误”经常伪装成玩法错误

一个购买按钮不出现，未必是阶段门禁写错；它可能收到一个被 `toNumber()` 截断的资源值。一次现实结算没有发生，也未必是自动化调度器停了；收益比较可能在转换为普通数字时变成 `Infinity`、`0` 或失去精度。读档后资源回到默认值，则可能是序列化器把大数对象当普通 JSON 数字处理。

排查时沿着数值生命周期走：

1. **来源：** 这个值来自原版对象、MOD 计算还是存档字段？
2. **表示：** 进入适配层时仍是 `Decimal`/`BigDouble`，还是已经变成 `Number`/`double`？
3. **操作：** 比较和运算调用的是大数 API，还是先做了普通数值转换？
4. **边界：** 错误发生在归一化、阈值、序列化还是显示格式化？
5. **回读：** 保存后重新加载，尾数、指数和阶段是否仍一致？

不要先把阈值改小来“证明”功能正常；那只会把数值表示错误掩盖成新的平衡问题。

## 可复用的测试策略

数值实现至少需要三类测试。

### 运算不变量

验证非零正常值始终满足归一化约定；验证 `x × 1 = x`、`x ÷ x = 1`（在允许精度内）、比较具有传递性，并单独覆盖零、负数、`NaN`、无穷大和最大指数附近的值。

### 边界与阈值

围绕 $10^{308}$、指数进位点、尾数刚好跨越比较阈值的值构造样本。不要只测 $10^{10}$ 这种普通数字，因为它绕开了大数类真正负责的部分。

### 跨端与存档往返

用同一组 `(mantissa, exponent)` 或等价输入分别交给 Web 与 Android，比较数量级、阈值结果和序列化往返。再把这些值放进合法阶段存档，执行读取、修改、保存、重启四步；“解析成功”不能替代“数值与阶段仍正确”。Web 仓库已有 `validate_number_currency.mjs`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/scripts/validate_number_currency.mjs；具体文件证据留在内部核验记录） 这类数值 API 检查入口，可作为新增回归测试的落点。

## 一条工程判断

超大数库不是 UI 的附属工具，而是游戏状态模型的一部分。它决定资源比较、自动化决策、重置收益、阶段门禁和存档兼容能否在同一套数量级上成立。跨端开发时，最安全的边界不是让两端共享一段看似相同的数学代码，而是为每端保留正确的本地表示，再用固定输入、阈值结果和存档往返建立可观察契约。

这套方法同样适用于移动端与 Web 的购物车、离线同步、编辑器状态和任何跨运行时系统：先找共同检查点，再比较转移，不要用最后一张截图替代整个过程。
