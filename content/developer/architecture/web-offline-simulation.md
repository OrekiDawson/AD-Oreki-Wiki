增量游戏里最容易误解的一件事是“离线了多久”。玩家看到的是浏览器重新打开后的结果，程序面对的却是至少三种时间：设备时钟经过的真实时间、存档记录的最后更新时间，以及游戏内部允许补算的模拟时间。把它们混成一个数字，就会出现资源重复增长、离线进度过少，或者浏览器挂起后下一次打开突然跨过多个阶段。

本文只讨论 Web 端的时间账本和离线模拟，不讨论自动购买策略本身。源码坐标固定在 Web 仓库提交 [`e1c93caa`](https://github.com/OrekiDawson/AD-Oreki-Edition-Web/tree/e1c93caa758de6c39cf814582123d4a35319eb25)，重点是 `src/game.js`、`src/core/storage/storage.js` 和 `src/core/intervals.js`。这些文件解释“时间怎样进入游戏”；它们不能单独证明某个浏览器或某份存档已经完成了真实运行验收。

## 三只钟不是一只钟

可以先用下面的模型阅读代码：

```text
设备时钟 Date.now()
        │
        ├─ 与 player.lastUpdate 的差值：本次可能的离线时长
        │
        ├─ 存档/设置门：是否允许离线进度、是否处于暂停或速跑状态
        │
        └─ simulateTime(diff)：把允许的差值分成游戏 tick 重新执行
```

`Date.now()` 只说明墙上经过了多少毫秒，不说明游戏应该无条件发放多少资源。`player.lastUpdate` 是上一次保存或加载边界留下的时间锚点；离线计算通常先用当前时间减去它。最后，`simulateTime()` 接收的是被策略允许的游戏时间，不是可以直接写进资源的奖励数。

这一区分很重要。设备时钟可能被调快，浏览器可能被系统挂起，用户也可能在导入存档后立刻加载另一份存档。可靠的实现应让这些情况经过同一条加载和模拟管线，而不是在界面层看到“离线几小时”后直接修改货币。

## 游戏循环怎样承接离线时间

`src/game.js` 的 `gameLoop(passDiff, options)` 处理在线帧和加载后的补算。在线时，`passDiff` 来自相邻循环；离线加载时，`GameStorage.loadPlayerObject()` 根据 `lastUpdate` 计算差值，必要时调用 `simulateTime(diff / 1000, false, fast)`。因此离线补算不是另一个“假的游戏模式”，而是用受控的时间输入重新经过生产、原版自动购买器和相关结算。

一次补算可以简化成：

```text
读取存档
  ├─ 解码、迁移、补齐默认字段
  ├─ 取得 lastUpdate 与当前真实时间
  ├─ 依据设置和运行状态决定是否 simulateTime
  ├─ 以若干游戏 tick 重放生产与结算
  └─ 重启定时器、刷新界面并更新下一次保存边界
```

`simulateTime` 的第三个参数用于快速模拟路径：源码注释说明，短离线时长可以限制 tick 数量，而较长时长仍需用更完整的方式推进。这里的“快”是减少重复循环的计算成本，不是跳过所有游戏规则。修改它时，必须说明哪些机制仍逐 tick 执行，哪些机制使用批量公式；否则一个性能优化可能悄悄改变离线收益。

## 为什么加载顺序比时间公式更重要

离线进度是在存档对象恢复之后发生的，而不是在原始文本刚解码时发生。`GameStorage.loadPlayerObject()` 先检查对象是否可识别，再执行版本迁移和默认字段合并；之后才根据 `lastUpdate` 判断是否模拟。这个顺序解决了一个很实际的问题：旧存档可能还没有新版本使用的离线开关、速跑字段或备份计时器，必须先迁移，模拟阶段才能读取完整状态。

加载顺序可以画成：

```text
序列化文本
   ↓ deserialize
可识别的玩家对象
   ↓ migrations + 默认字段
当前版本的玩家状态
   ↓ lastUpdate / offlineProgress
离线模拟
   ↓ postLoadStuff
可交互的游戏界面与定时器
```

如果在迁移前就读取 `offlineProgress`，缺字段可能被当成关闭；如果在 `postLoadStuff()` 之前让界面或定时器开始工作，旧的缓存和新的玩家对象就可能短暂不同步。排查离线问题时，不要只搜索 `simulateTime`，要沿这条完整管线确认每一步的输入。

## 保存不是离线模拟的尾注

`GameStorage.canSave()` 会拒绝若干不适合立即落盘的状态，例如正在选择符文、显示模拟进度条，或游戏已经进入禁止交互的结束状态。`save()` 通过序列化当前槽位根对象写入 `localStorage`；根对象包含当前槽位和多个存档槽，而不是只写当前玩家对象。

这带来两个工程约束：

1. 模拟结束后必须经过正常的收尾路径，重启游戏定时器、更新界面，并把新的时间边界写入后续保存；
2. 模拟过程中不能把“保存被暂时禁止”当作“存档已经更新”，否则下一次打开仍会用旧的 `lastUpdate` 重新补算同一段时间。

源码还区分普通保存与备份保存。离线加载时，`backupOfflineSlots()` 会根据经过的真实时间选择合适的备份槽；保存备份可以忽略模拟进度条，但这不等于可以绕过主存档的状态约束。设计备份或修改保存条件时，应分别回答“玩家当前槽位是否已经保存”和“能否留下一个模拟前的恢复点”。

## 时间漂移的四种来源

### 设备时钟被改变

`Date.now()` 不是可信的单调计时器。设备休眠、时区变化或人工修改系统时间都可能让差值变得异常。不要把所有异常差值都当作游戏逻辑错误；先记录存档中的 `lastUpdate`、加载时的当前时间和离线设置，再判断是否真的进入了模拟。

### 存档没有在正确边界更新

如果离线模拟完成后保存被 `canSave()` 拒绝，旧的 `lastUpdate` 仍会留下。下一次启动可能再次补算相同时间。这个问题的症状通常是“每次打开都得到一段相似收益”，应先查保存条件和序列化结果，而不是先调低收益倍率。

### 多槽切换混用了时间状态

`loadSlot()` 会保存当前槽、加载目标槽并重新读取备份时间。若新增缓存只保存在全局变量，却没有随槽位切换清除，就会把 A 槽的最后更新时间带给 B 槽。诊断时应把 `currentSlot`、玩家对象和备份时间当作一个整体检查。

### 模拟与在线循环重复推进

`simulateTime()` 结束后会进入统一的收尾逻辑，定时器再恢复在线 tick。若新代码在模拟期间额外启动在线循环，或在收尾时重复调用一次生产函数，资源会被计算两遍。性能优化必须先确认同一时间段只有一个推进者。

## 从症状定位到源码边界

遇到离线收益异常时，可以按以下顺序缩小范围：

1. **固定输入。** 导出存档副本，记录 `currentSlot`、`lastUpdate`、离线开关、速跑状态和设备时间；不要先反复打开同一份存档。
2. **确认是否进入模拟。** 查加载路径是否调用 `simulateTime`，还是因为游戏结束、速跑暂停或离线设置而直接走 `postLoadStuff()`。
3. **确认模拟时长。** 对照传入秒数、快速路径标志和实际执行的 tick；不要只用最终货币倒推时间。
4. **确认收尾保存。** 检查定时器是否重启、`lastUpdate` 是否在后续保存中更新，以及 `canSave()` 是否仍然阻止写入。
5. **隔离槽位和备份。** 在新槽位做最小实验，比较主存档和对应备份，避免用恢复操作覆盖唯一证据。

一个合格的回归用例应至少包含：在线运行并保存、关闭一段已知时长、重新加载、观察一次离线模拟、再次保存并重启。它要检查的是时间边界只消费一次、槽位没有串线、模拟后定时器恢复，而不是只比较“最后资源大约变多了”。设备时钟被人为调整的实验应单独标记，因为它测试的是时间信任边界，不是普通离线收益。

## 可迁移的设计经验

离线进度的核心经验可以迁移到下载续传、队列恢复和后台任务：把墙钟差值当作输入，把允许的模拟时长当作策略结果，把状态推进交给唯一的执行管线，把保存当作明确的提交边界。这样，性能优化可以替换模拟算法，却不会偷偷改变“时间已经被消费”的语义。

尤其要避免一个看似方便的接口：`grantOfflineReward(seconds)`。它把时间、生产、自动化、重置和保存揉成一个不可检查的奖励函数。更可诊断的接口是 `simulateTime(seconds, options)`，并在调用前后记录时间锚点、槽位和保存状态；当结果异常时，开发者能知道是输入时间错了、模拟路径漏了规则，还是提交边界没有成功。
