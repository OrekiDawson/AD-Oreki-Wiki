比较两份增量游戏存档，不能只问“哪个资源数字更大”。一份存档可能拥有更多现实机器，另一份可能还没现实却已经把永恒点数和挑战推进得更远；更高阶段的当前资源又可能在重置后变小。如果同步逻辑只挑最大的一个数字，结果很容易把真正更靠后的存档覆盖掉。

Web 端用 `ProgressChecker` 把这个问题拆成两个层次：先识别存档已经到达的最高阶段，再用阶段内的近似进度比较接近的存档。本文依据固定提交  [`b28b231efa5b694ce1da8a1e508cfc3ecc099344`](https://github.com/OrekiDawson/AD-Oreki-Edition-Web/tree/b28b231efa5b694ce1da8a1e508cfc3ecc099344)，重点阅读 `src/core/secret-formula/progress-checker.js`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/src/core/secret-formula/progress-checker.js） 与 `src/core/storage/progress-checker.js`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/src/core/storage/progress-checker.js）。它讨论的是比较算法，不是存档文本如何编码，也不是离线时间如何补算。

## 先承认：进度不是一条数轴

玩家直觉里的“进度”至少包含三种信息：

- **阶段**：是否完成过无限、永恒、时间膨胀、现实或某位天神；
- **阶段内积累**：当前阶段的资源、次数、升级或挑战完成度；
- **时间事实**：玩家实际投入过多少运行时间，某份存档是否可能是较旧的快照。

它们不能简单相加。阶段是离散的，阶段内资源通常是指数增长的，时间又是另一个维度。比较器因此采用一个有序阶段表，再给同一阶段的存档添加一小段近似的小数：

```text
存档
  └─ 从高到低找到第一个已达成阶段
        ↓
  阶段编号 + clamp(阶段内近似进度, 1)
        ↓
  只在差距足够大时判定明显领先
```

这不是给玩家排名，也不是生成精确的“完成百分比”。它的目标更窄：在两个候选存档明显不同的时候提供方向；接近时返回“不确定”，把选择交给上层流程或玩家。

## 阶段表扫描

`progressStages` 定义了从生产反物质、无限、打破无限、复制器、永恒、永恒挑战、时间膨胀，到现实、天神、虚幻机器、佩勒等阶段。每一项都有 `hasReached(save)`，还可能有建议资源和 `subProgressValue(save)`。

`ProgressChecker.getProgressStage(save)` 从数组末端向前检查，命中第一个阶段就停止。这样做的关键是：高阶段存档可能仍然保留低阶段字段，低阶段条件不能抢先把它归类。例如已经现实的存档仍可能有无限次数、永恒点数或时间膨胀数据；若从低到高扫描，算法会在第一个容易满足的条件处提前返回，后面的所有比较都会被降级。

阶段表最后保留一个总能命中的开局条件，避免合法但非常早期的存档得到“没有阶段”的异常。新增阶段时，不能只在数组中插一项；还要同时定义稳定的阶段 ID、真实可核验的 `hasReached` 和合理的阶段内进度函数，并检查扫描顺序。

## 阶段内近似

`getCompositeProgress(save)` 先取得阶段，再计算：

```text
composite = stage.id + min(subProgressValue(save), 1)
```

阶段 ID 保证不同阶段首先分开；小数部分只用来比较同一阶段附近的存档。源码注释明确说它是 rough interpolation：靠近前一阶段或后一阶段的数值有方向意义，但中间值不是绝对完成度。

这是一项有意的工程取舍。若要得到精确的全局进度，就必须为每个系统定义统一价值、处理重置保留项、平衡数量级，还要随着新机制不断重写评分函数。云冲突或恢复流程通常不值得承担这样的复杂度；“明显领先”“差不多”已经足以决定是否自动替换，接近的情况则应该保守处理。

## 阶段指标

阶段内函数必须选能代表该阶段方向、且能从原始存档对象读取的指标。例如：

- 开局阶段把星系、维度提升和反物质指数合成一个粗略值；
- 无限阶段结合无限次数与大坍缩自动器状态；
- 时间膨胀阶段使用膨胀时间的对数；
- 永恒挑战阶段把挑战完成数和永恒点数合在一起；
- 天神阶段使用投入量、碎片、宠物等级或成就数量；
- 佩勒阶段使用遗物等毁灭现实中的长期资源。

这些函数并不要求所有资源都单调，也不假装不同阶段的“一个小数点”具有相同物理意义。它们只需要满足一个更实用的性质：在同一阶段，明显更靠后的存档大概率得到更大的近似值；无法满足时，就应缩小结论或返回不确定。

## 存档对象边界

云比较和恢复流程处理的可能不是当前全局 `player`，而是刚解码、尚未安装到运行时的存档对象。`progress-checker.js` 的注释特别提醒，很多 Decimal 在这里仍是字符串，不能依赖只对当前玩家实例有效的访问器。

因此阶段函数应当：

- 从传入的 `save` 读取字段，而不是偷偷读取全局玩家；
- 对字符串数值显式构造 `Decimal`，不把超大数交给 JavaScript `Number`；
- 对可选的天神或后期字段使用安全的存在性判断；
- 不在比较过程中修改存档、运行迁移或触发游戏事件。

这条纯函数边界很重要。比较器若依赖当前页面、当前槽位或当前运行时缓存，同一份云存档在不同浏览器状态下可能得到不同结论；更糟的是，比较过程会产生副作用，导致“判断哪份更好”本身改变了游戏。

## 近似结果

`compareSaveProgress(first, second)` 计算两个 composite progress 的差值，只在差距超过一个小阈值时返回方向；差距很小时返回 `0`。这个 `0` 不是算法失败，而是安全设计：近似评分无法证明两份存档的真实差异，就不应该替玩家做不可逆覆盖。

上层流程可以据此区分：

```text
明显不同 → 给出明确的较前/较后方向
接近      → 显示冲突，让玩家选择或等待更多证据
无法读取  → 走格式/迁移错误，而不是当成“进度为零”
```

千万不要把 `0` 改成“默认本地优先”或“默认云端优先”而不记录原因。默认策略可以属于产品决策，但不能伪装成比较器已经证明哪份存档更好。

## 时间比较是另一条证据

源码还提供 `compareSaveTimes(first, second)`，比较 `records.realTimePlayed`，并在一方缺失时返回中性结果。时间不是进度的替代品：玩家可能挂机时间更长，却因为配置错误没有推进；也可能通过快速机制在更短时间内达到更高阶段。

正确的使用方式是把时间作为辅助证据：

- 阶段明显领先的存档，即使运行时间较短，也不能仅因时间少而被覆盖；
- 进度近似相同的存档，可以参考运行时间判断哪个更可能是较新的快照；
- 时间字段缺失、来源不同或经过迁移时，应降低结论强度，而不是补一个虚构的时间。

这也是为什么“最后修改时间”不等于“游戏进度时间”。前者描述文件，后者描述玩家实际在游戏中推进的记录；两者适合回答不同问题。

## 排查存档冲突的顺序

遇到云端、本地或多槽存档冲突时，可以按以下顺序缩小范围：

1. **先确认对象可解析。** 若解码或结构检查失败，先处理格式和迁移，不进入进度比较。
2. **再确认阶段。** 打印两份存档命中的阶段名称与 ID，检查是否因扫描顺序或字段缺失被降级。
3. **再确认阶段内指标。** 记录 `subProgressValue` 的输入字段和经过 `Decimal` 转换后的结果，不只看 composite 最终数字。
4. **再确认比较阈值。** 差距接近阈值时，应保留冲突，不要通过调大阈值制造“自动解决”。
5. **最后参考时间。** 只有在进度接近时，再比较 `realTimePlayed` 和存档来源。

如果某份晚期存档被判定为开局，优先检查后期字段是否存在、是否仍是字符串、`hasReached` 是否安全处理可选对象；不要先修改云端覆盖策略。如果阶段正确但方向反了，检查比较函数的返回值约定与调用者的排序方向，比较器返回码不应被当作普通的“分数差值”直接展示。

## 新增指标门禁

扩展进度比较器至少要回答四个问题：

1. 新阶段在旧阶段之后的真实判据是什么？
2. 它在原始存档对象上能否运行，而不依赖当前全局玩家？
3. 阶段内指标在 Decimal 字符串、缺字段和极端值下是否有安全结果？
4. 当两份存档接近时，比较器是否仍然返回保守的不确定，而不是强行排序？

定向测试应覆盖空存档、开局存档、跨阶段存档、同阶段接近存档、缺少后期字段的兼容存档，以及大数仍以字符串保存的对象。测试通过只能说明比较器的结构和方向符合预期；它不能证明某份云端数据一定是玩家想要的那份，最终覆盖仍需要可恢复备份和明确的产品策略。

## 可迁移的工程经验

这套算法适合任何“状态空间很大、不能精确排序、覆盖有风险”的系统：先用不可逆里程碑做粗分层，再用局部指标解决明显差异，把近似误差显式转成“不确定”。它比拼接几十个字段的总分更容易解释，也比选一个最大资源更不容易被重置语义欺骗。

最重要的不是 composite 数字长什么样，而是它承认自己的能力边界：它可以帮助发现明显更靠后的候选，不能替玩家决定所有冲突。对于不可逆的数据写入，保守地停下来请求选择，往往比自动做出一个看似聪明的覆盖更专业。
