游戏状态里有一类字段并不值得写进存档：它们可以由当前存档重新算出，却会在高频循环中被反复读取。例如时间研究树、维度共同倍率、最便宜的自动购买器，以及挑战入口看到的本轮峰值。Web 端把其中一部分包装成惰性缓存，让热路径读取一个已经算好的答案；代价是，改变依赖字段以后必须明确地撤销这个答案。

本文只讲模型层的缓存生命周期。效果怎样组合见[效果模型](/developer/architecture/effect-model)，界面怎样收到模型变化见 [Web 端反应式更新](/developer/architecture/web-ui-reactivity)。

## 三种状态

先把三个容易混淆的概念分开：

- **源状态**是 `player`、资源对象、购买记录和挑战记录中的事实。
- **派生状态**是由源状态计算出的答案，例如 `GameCache.timeStudies` 或维度倍率。
- **显示状态**是组件已经格式化的文字、按钮状态或进度条。

源状态正确、派生状态错误，通常是失效边界漏掉了；派生状态正确、显示状态错误，才应该追 UI 更新。缓存专题不负责修复源状态，也不应把“重新渲染”当成缓存修复。

## `Lazy` 做什么

Web 的 `src/core/cache.js` 中，`Lazy` 只有一个计算函数和一个可选的缓存值。第一次读取 `value` 时调用函数并保存结果，后续读取直接返回结果；`invalidate()` 把值恢复为未计算状态，下一次读取才会重新计算。 `invalidateOn(...events)` 只是把失效动作挂到事件上，并不会自动推断依赖。

```js
get value() {
  if (this._value === undefined) this._value = this._getValue();
  return this._value;
}

invalidate() {
  this._value = undefined;
}
```

这意味着 `Lazy` 不是依赖图。计算函数读取了什么，代码本身不会记录；写入路径也不会被运行时自动追踪。新增依赖时，必须同步检查所有会改变该依赖的购买、重置、读档和开发工具入口。

## `GameCache` 的依赖

`GameCache` 是一组按主题命名的 `Lazy` 实例，而不是一个统一的大缓存。`timeStudies` 从当前研究列表生成布尔数组；`currentStudyTree` 从当前研究集合建立树；`tickSpeedMultDecrease` 和 `dimensionMultDecrease` 从效果对象求和。`cheapestAntimatterAutobuyer` 则扫描尚未购买或解锁的自动购买器，返回当前最低成本。

不同缓存的失效粒度不同：购买时间研究时要使研究相关答案失效，符文变化时则要同时更新库存空间、效果汇总和静态权重。维度最终倍率甚至把数组的 `invalidate()` 改写为逐项失效；只清空数组外壳并不能清掉每一层 `Lazy`。

因此，代码审查不应只问“这里有没有缓存”，还要问“这个写操作改变了哪些缓存的输入”。一项新升级如果开始影响原本只依赖挑战奖励的倍率，却没有补上失效调用，错误不会立刻抛异常，只会稳定地滞后一轮。

## 全局清理与局部清理

购买路径适合定向失效：它知道自己改变了哪些机制，清理范围小，下一次读取只重算必要部分。现实重置和读档则会同时替换很多源字段，Web 代码使用 `Lazy.invalidateAll()` 作为跨系统清理；这仍不覆盖不属于 `Lazy` 的对象缓存。

例如挑战入口的 `ECTimeStudyState` 自己保存 `cachedCurrentRequirement`。它表示本轮运行见过的最高资源值，不是 `Lazy` 的 `_value`，所以重置时还要调用 `ECTimeStudyState.invalidateCachedRequirements()`。如果只做全局 `Lazy` 清理，挑战入口可能把上一轮峰值带入新一轮；如果只清理入口对象，普通倍率又可能继续使用旧值。

## 峰值不是瞬时值

`requirementCurrent` 的特殊之处在于它有意保留单调峰值：第一次读取当前资源后，后续读取只在新值更大时更新。这个值服务于“本轮曾经达到过多少”的条件，不能被当作实时资源显示。

这也解释了一个常见误判：重置后某个挑战入口仍然显示已经达到，问题未必在大数比较。应先区分持久的完成标记与本轮峰值缓存；前者代表历史事实，后者必须随新运行重新采样。两者的生命周期不同，不能用一个字段替代另一个。

## 沿症状定位

遇到“数据已经改变，结果却不变”，按这条链查：

1. 找到实际改变的源字段或机制集合，而不是只看按钮文字。
2. 找到读取结果的计算函数，列出它直接访问的字段和嵌套效果。
3. 沿购买、重置、读档路径寻找定向或全局失效调用。
4. 失效后强制冷读同一派生值；冷读正确说明问题在失效时机，仍错误才继续查公式或数值域。
5. 只有模型冷读正确而页面仍旧时，才转向事件和组件更新。

```text
源状态改变 → 依赖失效 → 下一次读取重新计算 → UI 读取新值
```

把这四步拆开，能避免用刷新页面掩盖真正的生命周期错误。

## 新增缓存的取舍

只在热路径确实反复读取且计算成本值得承担时引入缓存。一次性的冷路径如果没有性能问题，不应为了“统一”而增加失效负担。决定缓存后，最好在同一处说明计算函数、依赖和失效入口；对于本轮峰值、历史最佳值等有意累积的状态，还要把重置边界写进对象生命周期。
