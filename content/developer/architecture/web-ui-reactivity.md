Web 端的界面不是把 `player` 对象直接“打印”到页面上。游戏状态在主循环里持续变化，Vue 组件却不能为每一个字段都建立一条独立的推送链；如果每个购买、重置和计时器都立即触发整棵 DOM 重绘，游戏会把大量时间花在展示中间态上。

当前 Web 实现选择了另一种边界：游戏逻辑发出事件，`GameUI` 把一轮变化合并成一次 UI flush，组件通过 `GAME_EVENT.UPDATE` 读取状态并更新自己的投影。教程弹窗又在这个基础上加入阶段签名、阅读位置和低频重算，让“页面会跟着游戏变化”与“页面不会每帧重复做昂贵工作”同时成立。

本文依据 Web 固定提交 [`e1c93caa`](https://github.com/OrekiDawson/AD-Oreki-Edition-Web/tree/e1c93caa758de6c39cf814582123d4a35319eb25)，重点阅读 `src/core/event-hub.js`、`src/core/ui.js`、`src/components/modals/OrekiTutorialModal.js` 和教程状态模块。它不讨论 Web 离线时间的计算，也不把页面刷新误当成游戏逻辑或自动化动作。

## 先分清逻辑事件和界面事件

Web 端维护两个 `EventHub` 实例：`EventHub.logic` 面向游戏逻辑，`EventHub.ui` 面向组件。静态 `EventHub.dispatch(event, ...args)` 会先把事件送到逻辑通道，再交给 `GameUI.dispatch`，后者把 UI 事件放入待处理队列。

```text
一次游戏变化
      ↓
EventHub.logic：需要即时处理的逻辑监听器
      ↓
GameUI.dispatch：收集 UI 事件
      ↓ Promise microtask
EventHub.ui.dispatch：通知 Vue 组件 update()
      ↓
Vue 计算属性和 DOM 更新
```

这两条通道不能互换。逻辑监听器可能需要在重置前后立即维护数据结构；UI 监听器的任务是读取已经稳定的状态并投影到页面。如果把业务副作用塞进 UI `update()`，一次普通重绘就可能改变游戏；如果让每个组件都直接订阅全部逻辑事件，组件之间又会形成难以排序的隐式调用链。

`EventHub` 的监听器还记录所属 `target`。组件销毁时，`EventHub.ui.offAll(this)` 会移除该组件的监听，避免弹窗关闭后仍收到更新。这个清理动作看似只是内存管理，实际上也保护了状态正确性：一个已经不存在的组件如果继续响应事件，可能读到新存档并操作旧引用，表现为偶发的重复弹窗或控制台异常。

## `GameUI.flushEvents()` 为什么要延后一拍

`src/core/ui.js` 中的 `GameUI.dispatch` 不会每次调用都立即遍历所有组件。它先去重同名事件；如果尚未安排 flush，就使用 `Promise.resolve().then(...)` 安排一次微任务。随后 `flushEvents()` 批量派发已收集的事件，最后统一发出 `GAME_EVENT.UPDATE`。

这个设计有三个关键性质：

1. 同一个事件在一轮内不会因为多次底层写入而重复通知；
2. 不同事件可以先完成逻辑变化，再由组件读取最终状态；
3. `UPDATE` 是一次统一的“请重新读取”信号，而不是携带一份可能已经过期的完整快照。

可以把一轮更新想成提交事务：

```text
买升级 → 触发事件 → 重置又触发事件 → GameUI 合并
                                      ↓
                         组件只读最终 player 状态
```

因此组件的 `update()` 不应假设自己是唯一读者，也不应把上一次计算结果当成下一次的游戏真值。组件只负责从当前状态计算显示内容；真正的购买、重置和存档写入必须留在逻辑层。

## Vue 组件怎样接入这条管线

`ui.js` 给所有组件混入 `$viewModel` 计算属性，把 `state.view` 暴露为视图状态；组件若定义 `update()`，创建时会自动订阅 `GAME_EVENT.UPDATE`，并在 UI 已初始化时先执行一次。组件销毁时统一解除订阅。

这带来一个很容易被忽略的边界：组件的 `update()` 是“重新读取当前状态”，不是“接收一份更新后的参数”。当一个组件需要自己的派生值时，可以写在计算属性里；当它需要在事件后同步本地缓存时，才使用 `update()`。不要在 `update()` 中复制整份 `player`，那会重新制造一套不会自动迁移的状态。

项目还对 Vue 的计算属性 watcher 做了可重算包装。`$recompute(key)` 通过切换一个可观察标志，让指定的计算属性重新求值。这种机制解决的是“底层游戏对象不是 Vue 响应式对象”的问题：游戏核心可以保持自己的普通对象和高性能数值结构，Vue 只在需要时被明确通知重新读它们。

源码还提供 `ReactivityComplainer`，在开发环境检查 `player` 是否意外变成 Vue 的响应式对象。这个限制很有工程意义：如果把整个游戏状态树交给 Vue 代理，深层对象写入、超大数值和主循环性能都会变成 UI 框架的隐式成本。这里选择“普通游戏状态 + 显式 UI 更新”，换来的是更清晰的所有权。

## 事件去重不等于状态去重

`GameUI.dispatch` 会对事件名做队列级去重，但它不会替逻辑层判断两次变化是否具有相同语义。例如一次重置可能先发出 `BIG_CRUNCH_BEFORE`，再发出 `BIG_CRUNCH_AFTER`，最终 UI 队列通常关心的是刷新后的结果；而某些成就或日志监听器仍需要完整的逻辑事件顺序。

所以修改事件系统时要问两个问题：

- 这个事件是逻辑契约，还是 UI 重新读取的提示？
- 去重的是通知次数，还是游戏状态本身？

不能因为 UI 队列只处理一次 `UPDATE`，就删除逻辑层的前后事件；也不能因为两个 UI 事件最终都触发 `UPDATE`，就认为它们对组件没有不同的含义。事件系统优化的目标是减少重复投影，而不是压扁游戏状态转移。

## 教程弹窗：一个有边界的状态投影

`OrekiTutorialModal.js` 是观察这套架构的好例子。它读取 `TUTORIAL_CHAPTERS`、附录、当前阶段快照和 `TutorialReadingPosition`，负责展示、切章和恢复阅读位置；源码注释明确说明它不写 `player`，也不改变游戏开关。

教程组件的阶段更新不是每次 `GAME_EVENT.UPDATE` 都完整重算。`update()` 先增加 `frameTick`，每 15 帧才取得一次 `getTutorialStageSnapshot()`；新的阶段签名与旧签名相同，就直接返回。只有签名变化时，它才替换阶段快照，并在玩家尚未手动翻章、且当前不是附录时，把位置移到当前阶段章节。

这不是把信息“更新得不够快”，而是按照信息的变化频率选择成本：

```text
游戏数值：高频变化，交给普通组件在 UPDATE 中读取
教程阶段：低频变化，按帧间隔和状态签名检查
阅读位置：用户行为产生，单独保存，不随游戏 tick 覆盖
教程正文：静态数据，只负责渲染，不写入游戏状态
```

如果用户已经手动选择章节，阶段变化不能抢回焦点；如果打开附录，自动定位也不能把读者跳回主线。界面更新的正确性不仅是“数字新”，还包括不破坏用户正在进行的阅读意图。

## 生命周期与阅读位置为什么要分开

教程弹窗可能因为关闭、按 Esc、被更高优先级弹窗顶掉而销毁。组件在 `beforeDestroy()` 中通过弹窗队列判断自己是否仍在队列里：仍在队列通常表示被暂时顶掉，应保留章节和滚动位置；已经出队则表示用户关闭，下次主线章节应按当前阶段重新定位。附录作为查阅资料，则允许在显式关闭后记住位置。

滚动位置在滚动过程中写入 `TutorialReadingPosition`，而不是等销毁时再读取 `$refs.scroll.scrollTop`。这是因为销毁回调执行时 DOM 引用可能已经清掉，临时再读只会得到零。这个细节可迁移到任何可被异步销毁的组件：用户状态应在事件发生时保存，不应把最后一次 DOM 读取当成可靠提交点。

窄屏目录还会根据实际溢出方向选择横向或纵向滚动，并把当前章节滚入可视带。这里的关键不是 CSS 技巧，而是组件不把“屏幕宽度”当成唯一布局事实；它读取容器实际的 `scrollWidth/clientWidth` 和 `scrollHeight/clientHeight`，再决定滚动轴。响应式界面排障时也应优先观察真实布局边界，而不是只依据设备型号猜测。

## 常见故障怎样缩小范围

### 状态变了，但组件不刷新

先查逻辑是否调用了 `GameUI.dispatch` 或 `GameUI.update()`，再查组件是否在 `created()` 中定义并订阅了 `update()`。若事件已入队，继续看 flush 微任务是否被异常打断；不要先在组件里加定时器轮询。

### 页面重复刷新或性能突然下降

检查是否绕过 `GameUI.dispatch` 直接遍历组件，是否在一次逻辑操作中反复发同一 UI 事件，以及 `update()` 是否做了购买、格式化大表或同步 I/O。UI 事件应合并，昂贵的阶段判定应使用签名或合适的低频节拍。

### 弹窗关闭后仍报错

检查组件销毁时是否调用 `EventHub.ui.offAll(this)`，以及组件是否把匿名监听器注册到了别的全局对象。若错误只在切换存档或反复打开弹窗后出现，优先怀疑旧组件监听器泄漏，而不是游戏数值本身。

### 教程总是跳回当前阶段

核对 `navigated`、`stageSig` 和 `TutorialReadingPosition`：用户手动切章后不应再被阶段更新抢回；打开附录时也不应执行主线自动定位。只有内容数据确实变化时，才应更新章节快照。

### 数值显示旧，但其他组件正常

确认该组件是否依赖普通 `player` 深层字段，却没有在 `UPDATE` 中重新读取，或是否错误地把一次计算结果缓存为永久值。不要为了修一个组件，把整个 `player` 改造成 Vue 响应式树；先修它的订阅和派生值边界。

## 可迁移的工程经验

这套 Web UI 架构的核心不是 Vue API，而是明确的状态所有权：逻辑层改变游戏，事件层通知变化，组件层读取并投影，用户阅读状态单独保存。批量 flush 减少重复渲染，事件订阅清理避免幽灵组件，阶段签名避免低频信息每帧重算，实际容器尺寸则比设备标签更可靠。

当一个页面需要“自己维护一份真相”时，应先问它能否改成：从核心状态计算、由事件触发重新读取、在销毁时解除订阅。只有确实属于用户交互的阅读位置、滚动位置或临时输入，才值得拥有独立状态。这样，页面不会因为一次渲染变成第二个游戏内核，调试也能沿着“事件是否发出—队列是否 flush—组件是否读取—DOM 是否投影”逐段定位。
