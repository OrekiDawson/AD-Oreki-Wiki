游戏内教程最容易退化成两份互相漂移的文本：Web 改了章节，Android 仍显示旧稿；弹窗里修了一个术语，生成资产却没有更新；章节少了一个字段，界面不报错，只是悄悄少了一段内容。对读者来说，这些问题都像“教程偶尔不可信”；对开发者来说，根因是内容没有被当成有版本、有结构、有生成边界的数据产品。

当前项目把教程正文集中到一份 JSON，并让 Web 与 Android 分别消费它。本文依据固定源码提交 [`b28b231efa5b694ce1da8a1e508cfc3ecc099344`](https://github.com/OrekiDawson/AD-Oreki-Edition-Web/tree/b28b231efa5b694ce1da8a1e508cfc3ecc099344)，解释这条内容管线的契约、阶段派生、生成校验和排障方法。重点是“内容怎样可靠地到达两个运行时”，不是教程 UI 怎样排版，也不是玩家应当怎样推进游戏。

## 唯一内容源

`src/core/oreki-tutorial-data.json` 是正文的单一来源。它保存 `schemaVersion`、更新时间、阶段提示、章节和附录；章节正文由若干结构化字段组成，附录则是独立的查阅材料。`src/core/oreki-tutorial.js` 导入生成后的模块并暴露这些数据，但不在 JavaScript 中再写一份章节正文。

这条规则解决的不是格式偏好，而是所有权问题：

```text
JSON 正文
   ├─ Web 生成模块 → Web 教程读取器
   └─ Android 生成脚本 → Android 教程资产
```

如果渲染组件里再补一段“临时说明”，就会出现三个版本：JSON、Web 组件和 Android 资产。下一次翻译或术语修订时，没人能回答哪一份才是权威。正确的修复位置是内容源或生成器，而不是在某个按钮点击后临时替换字符串。

## 章节字段契约

当前章节围绕十类读者信息组织：阶段目标、进入条件、具体操作、购买优先级、自动化配置、挑战攻略、关键数值、完成判据、下一步和常见卡点。字段的价值在于让工具可以检查“章节是否完整”，而不是强迫每一章写成一样的文章。

例如，`steps` 应该是可执行步骤数组，`numbers` 是带标签的数值条目，`traps` 是可单独列出的常见卡点；它们不应被压成一段无法检查的富文本。字段契约还能让 Android 生成器和 Web 读取器分别决定自己的排版，而不把某个平台的 HTML 或 View 结构泄漏进正文源。

`schemaVersion` 则是结构版本，不是游戏版本。游戏升级可能只改变一个解锁数值，内容结构却保持不变；反过来，新增附录或改变字段类型，就应考虑结构版本。读取器遇到不认识的 schema 时应警告或拒绝猜测，不应把未知字段默默当成空字符串。

## Web 生成模块

浏览器端源码通过 `src/core/oreki-tutorial.js` 使用 `oreki-tutorial-data.gen.js`。生成脚本 `scripts/gen_tutorial_module.mjs`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/scripts/gen_tutorial_module.mjs；具体文件证据留在内部核验记录） 把 JSON 机械转换为 ESM 模块，生成文件顶部明确标记“自动生成，请勿手改”。

之所以保留这个中间层，是因为项目的浏览器兼容边界不保证直接使用 JSON module import。生成器让运行时只加载普通 JavaScript 模块，同时把源文件、生成命令和校验命令写进产物注释，降低“改了 JSON 但浏览器仍拿旧模块”的风险。

生成文件不是第二个内容源。它应该满足一个简单关系：

```text
parse(JSON) → serialize(ESM)
```

如果生成文件里出现手工修改，下一次生成就会覆盖它；如果生成文件与 JSON 不一致，应该修复生成流程或重新生成，而不是把生成物提交成“临时正确”。

## 阶段与展示

`oreki-tutorial.js` 还负责把玩家状态派生为教程阶段快照。阶段定义分别提供 `unlocked` 与 `entered` 判据，快照把每一层标为“已进入”“条件已满足，尚未进入”或“未解锁”。这三种状态不能压成一个布尔值：玩家可能已经解锁某机制，却还没有真正完成第一次进入；更高层结算还可能清理低层当前资源。

内容源只描述章节属于哪个阶段，阶段模块负责判断当前状态；章节正文不应自己读取 `player`，更不能在正文里暗示未解锁机制已经可用。对于未解锁章节，读取器提供统一的限制前缀，明确告诉读者“现在无法使用”，而不是把未来机制伪装成当前操作步骤。

这种分层也让同一份内容可以被不同客户端消费：

```text
游戏状态 → 阶段快照 → 章节可见状态
                    ↘ 内容字段 → Web/Android 各自排版
```

不要为了修一段教程文字，往 JSON 里加入当前客户端才能理解的 View ID、DOM 选择器或 Android 资源名；那会把内容数据变成渲染代码，重新制造平台分叉。

## 章节兼容性

章节使用稳定 ID，而不是把数组下标当作永久身份。读取器可以通过 `findTutorialEntry(id)` 在章节和附录中查找条目；阅读位置保存的是 ID 与滚动偏移，而不是一份章节对象。这样即使章节顺序调整，旧的阅读位置仍有机会定位到同一条内容。

校验脚本还检查章节 ID 唯一且连续。连续性适合当前主线章节，因为它能快速发现中间丢了一章；稳定 ID 则适合阅读恢复和跨生成物核对。两者解决的是不同问题，不能因为 ID 连续就把 `ch07` 当作“永远代表某个机制”。机制归属仍由章节字段和源码事实决定。

附录与主线章节也应保持不同语义。附录可以收录记数法、卡点对照或差异资料，但不应进入阶段推进链，也不应改变“下一步”计算。把附录误放进章节数组，会让玩家打开教程时跳到资料页，甚至让阶段定位误认为玩家已经进入了某个机制。

## 校验器应该拦什么错误

`scripts/validate_tutorial.mjs`（源码定位：OrekiDawson/AD-Oreki-Edition-Web@b28b231efa5b694ce1da8a1e508cfc3ecc099344/scripts/validate_tutorial.mjs；具体文件证据留在内部核验记录） 的价值不在于生成一串绿色数字，而在于把“内容结构错误”尽早变成失败。至少应检查：

- schema 版本是否是生成器支持的版本；
- 章节是否存在、ID 是否重复或断裂；
- 十个字段是否存在且类型正确；
- 非草稿章节是否缺少操作步骤；
- 生成的 ESM 是否与 JSON 内容一致；
- 术语、标题和正文中是否出现不允许的占位或明显混入。

这里要区分两类失败。字段类型错误是内容管线故障，应在构建或定向校验阶段阻断；玩家事实写错则是编辑事实核查问题，即使 JSON 结构完全合法也不能放行。机器校验能证明“形状正确”，不能替代 Lead 对最终中文和机制事实的逐篇复审。

## 从一次修改到两个运行时

修改教程正文时，建议沿这条最短路径：

1. 从固定 Android/Web 源码确认机制、术语和阶段条件；
2. 只编辑 `src/core/oreki-tutorial-data.json` 中对应字段；
3. 运行 `gen_tutorial_module.mjs` 生成 Web 模块；
4. 运行 `validate_tutorial.mjs`，确认源 JSON 与生成文件一致；
5. 由 Android 的同源生成流程消费同一 JSON，并核对其资产边界；
6. 逐端检查读取器是否能正确处理字段、阶段状态和附录边界。

不要直接编辑 `oreki-tutorial-data.gen.js`，也不要把 Android 生成资产反向复制回 JSON。更不要先改渲染器来“适应”一个结构不合法的章节；如果内容需要新字段，应先更新 schema、生成器、校验器和两端读取器，再迁移正文。

## 常见故障排查

### Web 显示旧正文

先比较 JSON 与 `oreki-tutorial-data.gen.js` 的内容和生成时间，再确认当前构建引用的 Commit。若生成文件落后，重新运行生成器；若源和生成物一致，再查浏览器部署产物或缓存身份。不要在组件里再加一份同名文案。

### Android 与 Web 章节数量不同

先核对两端是否消费同一 JSON 版本，再看 Android 生成脚本是否忽略了附录、草稿或未知字段。章节数量差异不一定是 UI 漏渲染，也可能是两个生成器对“主线章节”和“附录”的定义不一致。

### 章节能打开但某块内容消失

检查字段类型。空数组、空字符串和缺失字段在渲染器里可能有不同含义；不要用默认文本掩盖结构错误。校验器应把必填字段缺失标为失败，读取器则应对可选字段提供明确的空状态。

### 未解锁章节写得像当前可用

检查阶段 `unlocked/entered` 的来源和章节 `stageKey`，再确认读取器是否应用统一的锁定前缀。不要只改标题加“未来”，因为正文中的操作步骤和购买条件仍可能误导玩家。

### 改了术语却出现双端不一致

搜索 JSON、生成文件、两端生成资产和渲染组件中的重复字符串。正确目标是只保留 JSON 中的一份正文；如果组件需要 UI 标签，应使用独立的界面术语，而不是复制章节正文。

## 可迁移的工程经验

教程管线其实是一种小型内容编译器：JSON 是源语言，生成的 ESM 或 Android 资产是目标格式，schema 和校验器是类型检查，阶段快照则是运行时上下文。把正文放进渲染代码，就像把业务规则写进 APK 的某个按钮回调；短期省事，长期失去可校验的边界。

这套方法也适用于帮助中心、任务说明和版本化知识库：用稳定 ID 管理条目，用结构字段表达读者任务，用生成器适配不同平台，用校验器拦截形状错误，用人工复审保证事实和文笔。这样内容可以变得更丰富，却不会因为多一个客户端就多出一份互相矛盾的“真相”。
