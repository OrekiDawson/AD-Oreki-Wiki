## 2. Wiki 内容与发布

### 2.1 内容规范、玩家与开发者专区

- 本仓是中文知识库，公开内容规范以 `content/wiki-rules.md` 为总纲，另以 `content/wiki-not.md`（本站不是什么）明确正文收录边界：不以 PR 日志、宣传稿、未经审核 AI 草稿或资料堆砌充当百科；允许经核验的玩家攻略、开发者手册与可复核工程研究。写作前核实正文、原始来源、模板和 `docs/AGENT_GUIDE.md`。区分原版、MOD、历史、当前实测与推断；禁止虚构 SHA、ABI、测试结果、下载或上线状态。遵守 CC BY-SA 4.0 与各原始资料的许可、署名、翻译术语和版本溯源。
- **共同编辑目标（2026-11-26）**：准确性是底线，可读性是基本要求，趣味性是重要质量目标。玩家与开发者正文应使用自然、有节奏、有思想的简体中文，减少 AI 腔、报告腔和公文腔；可根据主题加入有来源的机制揭秘、历史背景、数学趣闻、设计取舍、适度比喻或幽默，鼓励读者继续阅读和探索内链。趣味不得虚构事实、机制、历史或原理，不滥用感叹号、网络梗、Emoji、夸张修辞或刻意卖萌。文章仍按读者任务自由组织，不强制统一章节；原版译文保持逐段忠实、术语/公式/数值准确及 CC BY-SA 4.0 署名，不向译文正文混入本站原创发挥。
- **单站双专区**：`/player/` 面向普通玩家，含游戏百科、中文译文、MOD 玩法、教程、下载与 FAQ；`/developer/` 面向开发者，含架构、逆向、ABI、构建、故障、CI 和运行证据。共同规则/版权放公共区。混合文章按用途拆分，以来源和交叉链接避免事实重复与漂移。
- **下一次正式交付 P0 门禁**：下一次 Wiki 正式交付前，必须真实上线 `https://wiki.oreki.net/player/` 与 `https://wiki.oreki.net/developer/`，两个专区均有真实正文、独立分类导航和明确首页入口；验证移动端、搜索、面包屑、旧 URL 兼容、Quartz 构建、GitHub Required Checks、Pages HTTPS 和实际线上响应。关键项任一失败均为 `BLOCKED`；空目录、占位页、README 计划或仅 CI PASS 不能冒充双专区正式上线。完成后继续长期维护。
- **阅读体验与专区边界**：玩家专区以“新玩家能开始、当前阶段能推进、遇到困难能处理”为目标；开发者专区帮助真实开发者上手、理解架构、定位源码、验证与排障。玩家正文不塞 Kotlin/ABI/PR 流水账或项目审计，开发者正文不靠历史 PR/Run 和统一状态表凑篇幅。共同规则/版权独立；一项事实只维护一个权威解释，保留重要来源、旧 URL 和别名；纯文档 PR 不触发无关游戏长跑。
- **玩家专区按问题和阅读目的重构（2026-11-22）**：保留 `/player/` 公开路径与翻译署名，玩家正文分为**机制百科、入门教程、分阶段攻略、FAQ/故障处理、原版译文**五种用途；不将它们混成按 R 轮次汇编的“玩家技术报告”。机制百科回答“为什么”，教程回答“怎样第一次完成”，攻略回答“下一步如何选择”，FAQ 回答“当前问题如何处理”，译文只忠实呈现原版修订并有独立版权和审校状态。**不按固定“背景/意义/总结/参考资料”目录套写全部页面**，更不能用一句大而空的建议代替可操作路径。内容应按新档、无限、永恒、现实、天神/终局可渐进阅读，支持具体机制查找。
- **全站原创作者化整改 P0（2026-11-27）**：十篇标杆稿只是质量参照，不代表全站完成。Lead 必须逐篇阅读玩家专区、开发者专区、首页、专题页、教程、攻略及其他公开原创内容，建立作者化整改台账并按成熟风格保留、深度润色、重组重写、重新研究撰写或边界调整后重写分类；未逐篇阅读不得标记合格。允许科普、叙事、数学探索、专题随笔和技术深文等不同体裁，不得用统一模板、改标题/导语、只增趣闻章节、删减知识或加入主观感想冒充实质整改。每篇完成后 Lead 亲自复审事实、知识深度、结构、中文文笔、作者特色、趣味、来源、版权和移动阅读效果，成熟一批、审查一批、上线一批；全部原创页面逐篇判断且不合格页面完成上线验收前，不得宣告全站内容质量恢复完成。原版译文不适用自由改写，仍以忠实原文为首要原则。
- **作者化表达独立验收（2026-11-27）**：三份逐页台账必须把“作者化表达”作为独立字段，不得与正文修改状态、Lead 正文复审或合并/上线状态合并。适用原创页面只能按“待评估、 不合格、整改中、待复审、合格”记录；原版忠实译文等不适用页面记录“不适用”。已合并、已上线、CI PASS 或 Kody PASS 均不得自动推导为“合格”；Lead 必须完整阅读并确认作者化表达后才能标记合格。全部适用公开原创页面均达到“合格”前，R130 不得完成。
- **玩家事实与版本边界**：原版 Android 3.21.0、Web 冻结基线、当前 Android/Web MOD 和各自的真实游戏界面/源码必须分开标注；原版解锁和资源数值、MOD 缩放、调度器实际托管字段、存档互通与发布状态逐项核对；尤其禁止把历史实现、未合并 PR、旧版错误显示或目标体验表当作当前玩家事实。项目“真实新档 ≤180 分钟”是**目标/有条件的测试结果**而非所有玩家/版本保证，五阶段时段是体验设计而非强制具体解锁时间。无依据的攻略推荐、绝对化时间和跨平台等价宣称必须删除或注明未验证。
- **玩家正文质量门槛**：教程必须有真实界面/操作名称、前提、按序动作、到达下一步的判断和常见误区；机制页先解释资源、重置、保留项与解锁的因果；攻略应说明所依赖的存档阶段、难度/版本、选择原因和替代路线，不能把唯一最优路线写成已验证通用定律；FAQ 先给安全、可执行的排查步骤，危险的清档/改档/安装行为必须提示备份；原版译文逐段核对并如实记录 `TRANSLATED / STRUCTURE CHECKED / REVIEWED / VERIFIED AGAINST GAME`。首次使用的术语保持一致，较难的数值可辅以正确例子，**不复制工程报告或大量 AI 套话**。
- **玩家编辑与旧稿治理**：须完成原始事实核查、自然中文写作、作者自检并记录未执行项；Subagent 撰写、翻译或修改的正文必须由 Lead 亲自完整阅读最终候选，逐篇复核事实、文笔、趣味、深度、结构、用途和译文/版权，必要时直接润色或退回整改。独立审稿人可选，但不能替代 Lead；未经 Lead 复审一律标 `EDITORIAL_BLOCKED`，不得合并或发布。PR Ready、Kody 与 Quartz PASS 仍分别只是对应门禁结果，不能互相替代。存量先核对已有 77 个 `/player/` 页面（其中 61 个是 `/player/original/` 文件，含索引），九篇候选改稿 #81–#83 **不得因已写完便自动获放行**；先完成作者自检与 Lead 复审，再考虑导航与批量拓展。公开细则及逐页台账以 `content/wiki-rules.md`、`docs/玩家专区重构台账.md` 为准。
- **开发者专区全量重写（2026-11-26）**：`/developer/` 正式正文必须从真实 Android/Web 源码、当前构建链和原始技术资料重新构思、重新撰写。旧文章只作事实核查线索，不得作为写作底稿；换词、调序、补链接或拼接旧段落不算重写。允许重新设计标题、章节、叙述逻辑和信息架构；历史报告、原始证据、版权信息和有效旧 URL 保留于历史/证据层或通过 alias 兼容。已按本标准重写并经 Lead 逐篇完整审阅的文章不重复重写。
- **以读者任务划分四类内容**：①入门教程（从干净环境完成一件小事）；②操作指南（在明确前提下执行构建/测试/部署/排障）；③技术参考（入口、文件、符号、参数、配置和约束）；④原理说明（模块职责、调用链、数据流、关键权衡）。历史事件、R 轮次、CI 时间线仅作为独立档案和证据，不能冒充上述任一类；同一篇可交叉链接，**禁止强制统一标题模板**。
- **开发者质量硬门槛**：每篇先定义具体读者问题与适用 Android/Web 版本。讲架构须指出真实模块和调用/数据路径，必要时给准确图示；讲操作须给出已核实的前置环境、从仓库根可定位的命令/步骤、成功判据与失败定位；讲参考须列真实符号、文件与配置语义；讲故障须能复现、缩小范围并给出证据。源码/脚本引用优先固定 Commit，引用外部规范保留原始修订信息；**不能确认的路径、命令、数字或输出不得臆造**，未执行标 `NOT RUN`，不可把作者阅读视为运行 PASS。无需每篇同时塞入四种类型内容。
- **开发者正文反流水账**：正式技术文章不得按 R 轮次、日期、PR 或 Agent 工作记录罗列开发过程，不得堆砌 PASS/FAIL/BLOCKED/NOT RUN、SHA、Issue 或路径而不解释技术意义，不得把规则、任务书、验收报告改写成正文，不得使用空泛模板或大量表格代替连贯技术叙述。历史开发记录统一进入 `content/developer/history/` 或证据层；正文应围绕技术是什么、为何采用、如何运作、难点、使用/修改/排查和可迁移经验展开。
- **逐页进度清单（2026-11-26）**：Lead 必须依据当前 `content/` 实际文件树维护 `docs/全站重构页面台账.md`、`docs/玩家专区重构台账.md`、`docs/开发者专区重构台账.md`，每篇独立记录标题、路径、规范 URL、专区/类型、处理方式、状态、负责人、PR/Commit、Lead 正文复审、合并和线上验收。旧入口只列内部迁移清单，AI 草稿标明排除公开构建；不得使用过期总数、漏登页面或以台账更新冒充正文进展。页面状态统一为“未修改、重写或修改中、正文完成待 Lead 复审、Lead 复审通过待合并、已合并待上线验收、已上线验收、保留档案/兼容入口/已归档”。每批正文、复审、合并和线上验收后同步更新；Lead 对完整性和真实性负责。
- **Wiki 并行写作与集中交付（2026-11-26）**：废止“仅配置一名 Wiki Subagent”的限制。资源、安全和文件 Owner 允许时，Lead 可并行派发最多 5 名不冲突的 Wiki Subagent，按 Android/DEX、Web/双端、构建交付、参考排障、玩家/译文等主题一次认领 3–6 篇，复用同一批源码资料。Subagent 不得共享修改同一正文或台账；每篇完成即可滚动交 Lead 全文复审，未复审仍为 `EDITORIAL_BLOCKED`。Lead 在等待 CI/Kody/Pages 时继续审阅和调度独立内容；相关 3–6 篇集中为一个 PR，开放 PR 总数仍遵守六仓上限 5，写作并发不等于新增 PR。
- **开发者内容核查与 Lead 复审**：正式新增或大改须经源码/原始资料核对、从零构思写作、作者自检和未运行范围记录；Subagent 完成后 Lead 必须亲自完整阅读最终候选正文，检查事实、来源、中文、趣味、技术深度、结构、用途、版权与旧 URL，并直接润色或要求定向整改后复核。未经 Lead 正文复审一律标 `EDITORIAL_BLOCKED`，不得合并或发布；后续实质性修改只需重新复审受影响部分。发现实际问题或复审未完成均阻断；小幅文字/链接改动也须由 Lead 做与 Diff 对应的定向复核。
- **导航与技术档案**：将“开始开发→架构定位→构建与验证→排障与发布”作为未来主导航的四条读者路径，状态、来源、历史、AI 摘要放辅助入口。优先修复开发者首页、项目入门、Android/Web 架构、AGP 操作手册和故障排查这组核心页面，**但本规则 PR 不自动移动路径或发布未经复审的正文**。公开写作原则见 `content/wiki-rules.md`；开发者文章的执行流程和技术核查见 `docs/AGENT_GUIDE.md`、`docs/ARTICLE_TEMPLATE.md` 及本文件。

- **通用内容门禁**：玩家与开发者新稿/大改均须源材料核对 → 按真实读者任务写作 → 作者完成事实、步骤、版权、链接和未运行范围自检 → Lead 阅读最终候选正文。Lead 自己撰写的文章执行作者自检并记录范围；Subagent 文章不得以汇报、Diff、CI 或 Kody 摘要代替 Lead 逐篇正文复审。原版翻译还须符合独立翻译/版权政策，`STRUCTURE CHECKED` 不能冒充 `REVIEWED`。未完成 Lead 复审或发现实际内容/版权问题均标 `EDITORIAL_BLOCKED`；CI/Kody 和模型自评不代替正文复审。实际文件改动的 Wiki PR 仍必须取得 Kody Balanced 的真实 PASS；`skipped`、`KODY NOT RUN`、运行中、失败或 Provider 不可用均不是 PASS，不能合并。
- **AI Summary 是可选附属资料，不是开发者内容分类**：只允许在经独立核实的开发者技术正文后附已审核、默认折叠、带来源和适用版本的摘要；不得将 `AI Summary` 放到开发者主学习导航、作为文章替代品或发布 KPI。玩家正文无机器摘要；未审 `content/ai-drafts/` 永不进入公开 HTML、RSS、搜索与索引。现有 AI Summary 索引在后续导航重构时安全降级，不在规则 PR 中直接删历史文件。

- **公开内容与核验记录必须分层（Wiki 内容长期强制）**：玩家文章只保留有阅读价值、真实可追踪的来源与必要版本边界，不得在正文、脚注或每条参考文献后反复插入 `NOT RUN`、`HTTP 200`、`API 核对`、`revid 归属证明`、Kody/CI/PR 处理记录、核验模板和一串审查用技术括号；验证日志、未运行项及证据详情集中写入 PR 说明、Review Threads 或内部来源核验记录。开发者的构建、测试与故障文章可按真实任务需要呈现验证状态，但不以报告流水账代替技术解释。不得因清理冗余而假称来源已验证；未经查实的关键来源、数字或解锁条件必须先核对，仍无法确认的内容保留具体事实阻断、寻找可靠替代或暂不公开。
- **公开页面的链接治理（长期强制）**：`content/` 中进入 Quartz 的公开页面不得出现指向 GitHub 具体文件的 `/blob/`、`/raw/` 或 `raw.githubusercontent.com` 外链；该规则同样适用于玩家、开发者、原版译文、首页和公开方针。已有知识使用 Wiki 内链，尚无对应条目则先补充本站内容；源码说明保留必要代码片段、仓库/版本/路径/符号信息，具体文件和代码行证据放在内部审阅记录、维护文档或事实核验台账。GitHub 仓库首页、Release、Issue、PR、Commit 页面仍可按实际用途保留。CI 必须同时扫描 Markdown 源文件与构建后的公开 HTML；不得用隐藏、别名或改写脚本绕过检查，也不得为消除外链删除必要知识、来源或版权署名。
- **Kody 意见与文章质量分开判断**：Kody Balanced 对所有有真实改动的 Wiki PR 仍是用户要求的必经审查，不把 `skipped`、待审或 `NOT RUN` 冒充通过；但 Kody finding 属于待判断的问题线索，不是写作模板，也不得凌驾于用户明确授权。先识别真实缺陷，再以不伤害读者体验的最小修改修复；不能为迎合审查而机械复制机器核验状态、不断增加括号或把 Kody 必审改成可选。`EDITORIAL_BLOCKED` 表示实际事实、版权、误导、可用性缺陷，或 Subagent 正文尚未完成 Lead 复审；审查、CI 与 Provider 阻断另记 `REVIEW_BLOCKED(原因)`。缺少第二文笔审稿人本身不阻断，但不能跳过 Lead 复审。
- **文章可读性回归与外部等待防空转**：新稿、大幅改写与 Kody 整改提交前，检查正文是否自然连贯、读者能否照着操作、参考资料是否重复、是否混入审查状态或机器报告腔；发现此类污染视为内容质量回归，先定点修复，不无故全文重写。等待同一 HEAD 的 Kody/CI 回执时只记录必要状态和下一动作，转做其他独立任务或结束当前执行；不得靠空轮询、重复 `@kody start-review`、空提交消耗资源。
