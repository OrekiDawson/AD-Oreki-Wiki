# Wiki Agent 检索与编写指引

本文件说明怎样**找到正确资料并完成一项可审校的文档修改**，不是第二份规则正文。公开规则以 [知识库规则](../content/wiki-rules.md) 为准；跨仓授权、预算、优先级、任务编号依 [Workspace AGENTS.md](https://github.com/OrekiDawson/AD-Oreki-Edition-Workspace/blob/3652a9589251281c231f9b133ccd412ab83b7580/AGENTS.md)，本仓执行边界依根 `AGENTS.md`。

首页是面向人类读者的百科门户，不是项目管理面板，也不只是导航中转站。精选条目、趣闻和成长路线必须来自已复审正文并提供内链。Lead 可依据知识主题和读者任务拆分、合并、新建或归档页面；调整文章边界时同步链接、兼容入口、分类与逐页台账，不以旧文件数量限制重构。

## 写得准确，也写得值得读

编辑的质量目标按优先顺序理解为：准确性是底线，可读性是基本要求，趣味性是重要质量目标。先核对事实，再用自然、有节奏的中文讲清楚问题；不要把 PR、CI、状态表或 AI Summary 当成正文。文章可以用有来源的机制揭秘、数学趣闻、历史背景、设计取舍、源码片段、流程图或适度幽默帮助读者理解，但不能为了好看补写未经证实的机制，也不要滥用网络梗、Emoji、感叹号和夸张语气。

玩家页应让人既知道怎么操作，也明白为什么会这样；开发者页应让人既能完成任务，也能从真实故障、调用链和设计权衡中获得可迁移的技术知识。原版翻译仍逐段忠实，本站趣闻与 MOD 解释放在译文之外。选择结构时以读者问题为准，不因本指引而把所有文章套成同一目录。

标题命名例外：普通百科、攻略和技术文章使用自然中文标题；`content/player/original/` 下的正式原版译文使用“原版:条目名”，原版翻译专区首页不加前缀；正式方针和站务页使用“反物质维度MOD Wiki:方针名”。使用英文半角冒号且不加空格，保留原 URL、文件路径、aliases、original_title、修订号和版权字段。

## 接到任务时先确认范围

1. 确认用户要求改的是**玩家机制百科/教程/攻略/FAQ、开发者文档、原版翻译、网站配置**中的哪一种；“质量差”不等于授权自动改写所有页面、自动部署或启动付费 AI 审查。
2. 确认最新 `main`、现有开放 PR 与文件归属。已有审校中 Draft PR 不得被别的 Agent 覆盖；历史报告不等于现行技术事实。
3. 记录此页希望让人完成的具体任务，例如“找到 Android 自动购买器的策略入口”“在受支持的环境下运行一次定向测试”。没有明确的读者任务则先缩小主题，不用章节模板凑出一篇文章。
4. 对大幅改稿，先抽查现有 URL、入站引用、版本适用范围、保留的独有事实与旧证据；确定是**保留、定点精修、历史归档还是合并并重定向**，不盲目迁移或删除。

## 事实读取顺序

- **原版游戏玩法**：原版官方源码、对应版本的 wiki.gg 原始修订和许可证，再比对本站原版翻译的来源字段；`STRUCTURE CHECKED` 不意味着语义可靠。
- **Android 实现**：[Android 仓库](https://github.com/OrekiDawson/AD-Oreki-Edition-Android) 的现行 Kotlin、官方基线清单、构建入口、测试源码，再查相关固定 Commit 的报告/PR/Run。混淆符号和历史验证不可凭名称猜语义。
- **Web 实现**：[Web 仓库](https://github.com/OrekiDawson/AD-Oreki-Edition-Web) 的冻结源码和实际 MOD JS、测试和工作流；不得把 Android 代码路径复制成 Web 入口。
- **规则与交付**：Workspace `AGENTS.md` 管跨仓规则；Android/Web 各自 `AGENTS.md` 管平台技术细节；Wiki `content/wiki-rules.md` 管文章。Wiki 不复制大段规则制造多个权威版本。
- **当前状态**：PR、CI、Run、设备日志、真实存档或发布记录按准确候选判定。唯一权威事实来自来源仓库，Wiki 只做可查证的编辑整理。

## 玩家文章的五种用途

先从真实玩家问题而不是现有开发日志选题：

| 玩家任务 | 对应文章 | 重点检查 |
| --- | --- | --- |
| 理解一个系统与资源、重置规则 | 机制百科 | 资源/解锁/保留项与原版、MOD 数值的区别 |
| 从新档完成第一次操作 | 入门教程 | 真实按钮、顺序、正常结果与下一步 |
| 决定无限/永恒/现实/天神阶段如何推进 | 分阶段攻略 | 适用版本、存档条件、策略前提、备选方案，不承诺唯一最优 |
| 修复打不开按钮、自动化或存档异常 | FAQ/故障指引 | 非破坏性检查、存档备份、实际资源/研究前置、报告方式 |
| 阅读原版 Wiki 的中文文本 | 原版翻译 | 固定原文修订、忠实逐段、许可、署名及审校等级 |

原版与 Oreki Edition Android/Web 不可混写成一个“当前行为”。优先读取原版源码/真实修订和本项目当前实际源码、实际游戏/发布证据。玩家文章不能只引用其他 Wiki 文稿循环自证；引用原版译文的 `STRUCTURE CHECKED` 不等于事实独立复核。

审校 #81–#83 的九篇候选稿时，按各文章用途检查关键数值、条件、玩家真实操作、中文是否自然、手机阅读与来源 URL；不得把 Ready、CI PASS 或 Kody Review 写成事实核查或运行证据；作者自检须列明核对过的来源、条件与实际执行情况。最新候选状态须按 GitHub PR HEAD 回读，修订完成后 Lead 必须亲自阅读全文，记录复审范围、结论与未运行项；未经 Lead 复审不得合并。独立审稿人不是强制前置，但不能替代 Lead。具体优先级、待审页面清单见 [玩家专区重构台账](玩家专区重构台账.md)。

## 开发者文章的四种用途

| 读者需求 | 选择 | 验收重点 |
| --- | --- | --- |
| 从零完成一个小改动 | 入门教程 | 实际前提、按序操作、可观察的结果 |
| 完成某个操作 | 操作指南 | 真实命令、输入、预期产物、失败恢复 |
| 查参数/调用契约 | 技术参考 | 定义、类型、边界、固定源码版本 |
| 理解设计 | 原理说明 | 主要模块、调用与数据流、权衡、真实依据 |

选用 [不同用途的样板](ARTICLE_TEMPLATE.md)，**不要**让每篇都出现“背景、已确认与未确认、如何验证、历史变化”这些固定章节。真实历史放 `content/developer/history/`，引用但不搬运整篇日志；AI Summary 是可选的末尾附录，不进入主学习路径。

## 开发者内容重构顺序

开发者专区正式文章实行全量正文重写：旧稿只用于定位事实、历史证据和旧 URL，不得当作写作底稿；换词、调序、补链接或拼接旧段落不算重写。每篇从当前 Android/Web 源码、构建链和原始资料重新确定读者问题、标题、结构与解释。历史报告和证据保留在辅助层，完成标准重写并通过 Lead 逐篇正文复审的页面不重复重写。

开发者正文不是开发日志、周报、审计报告或 Agent 工作记录：禁止按 R/日期/PR 罗列过程，禁止堆砌状态词、SHA、Issue 和路径，禁止把规则、任务书、验收报告改写成技术文章，禁止用空泛模板或大量表格代替解释。正文应围绕技术机制、设计原因、内部运作、难点、使用/修改/排查和可迁移经验组织；历史过程放入历史档案。

每批开始前先按当前文件树回读三份逐页台账；每篇独立登记标题、规范 URL、类型、处理方式、负责人、PR/Commit、Lead 复审、合并和线上验收。旧入口只登记为内部 alias 迁移，AI 草稿明确排除公开构建。正文、复审、合并或线上验收发生后立即更新对应行；不要用过期总数、抽查记录或台账本身冒充内容进展。

有足够资源和不冲突文件时，Lead 可并行调度最多 5 名 Subagent，每名认领 3–6 篇同主题正文；共享源码核查结果，但不共享写入正文或台账。文章完成一篇就滚动交 Lead 全文复审，Subagent 继续组内其他文章；相关文章集中进入小批量 PR，等待 Kody/CI/Pages 时继续其他独立复审和写作。

若出现全站内容质量退化，以上并行写作规则自动让位于 P0 内容恢复：暂停批量拆分、合并、重写、改名和新增文章。Lead 先建立 Git 历史逐页对照台账，保留已验证技术整改；Subagent 仅做来源、图片和事实核验准备。Lead 亲自完成“反物质维度”“无限”“永恒”“现实”“天神”五篇标杆并交用户确认编辑方向，确认前不得批量推广。

优先按小批次处理：**开发者入口与上手 → Android/Web 架构和真实模块 → AGP 构建与验证 → 典型问题排查**。这些页面先做出可操作标杆，再逐页处理原有其他页面；现有内容分类和旧路由保持不变，真正迁移到新结构时再测试 alias、搜索、面包屑与移动端。40 页的基线、优先级与逐页待审状态见 [开发者专区重构台账](开发者专区重构台账.md)，不能将“已抽查”理解成审校完成。

- 开发者首页不能只是目录：应能从“我要开始贡献 / 定位代码 / 构建测试 / 排查问题”进入相应页面。
- 架构页须在当前源码中找出实际模块职责、入口和数据路径，不能只抄产品目标或工具名。
- 构建与排障页须核实命令是否在仓库存在、在何种环境运行、需什么输入、能怎样判断结果；无环境时不宣称“已验证”。
- 技术参考页不必写教程，但符号、文件、参数、副作用和版本边界必须准确；外链历史依据优先固定 Commit。
- 若技术材料从玩家页移出，必须先在开发者专题或原仓保存并更新引用，不能边删除边丢掉独有的 ABI/条件/恢复证据。

## 交付与审校

1. 先**核验源资料**，记录关键字段、版本与出处；没有原始来源则将结论列为待核实，不靠旧 Wiki 页面循环引用。
2. **重新撰写正文**，从源码和原始资料建立事实，用具体例子讲明读者如何完成任务；保留简体中文标题和需要的技术原拼写。不一次生成几十篇形式相似的新稿，也不能把旧文换皮称为重写。
3. **作者完成定向自检并由 Lead 复审**：作者按文章用途检查重要事实、实际命令和阅读体验，记录检查过的路径、是否执行命令及剩余 `NOT RUN/BLOCKED`；随后 Lead 必须亲自完整阅读最终正文，必要时润色或要求整改后复核。未经 Lead 正文复审标 `EDITORIAL_BLOCKED`，不得合并或发布；Lead 自己撰写的文章执行作者自检。Kody 审查和 Quartz 构建不能代替事实核查或正文复审。
4. 做最小相关机器检查（frontmatter、断链、隐私扫描、构建）。是否运行 Android/Web 测试应由改动范围决定，纯文档不机械触发游戏长跑。
5. 只有完成质量和 GitHub 合并门禁才可以公开。未完成 Lead 正文复审、或存在事实、版权、可操作性问题时标 `EDITORIAL_BLOCKED` 并修复；Kody、CI 或 Pages 阻断另按对应门禁记录，未取得 Kody Balanced PASS 不得合并，不为赶频率/凑页面数量合并。
6. 向 PR 记录：**更改的读者任务、核对的源代码 Commit 与文件、执行的命令/测试（或 NOT RUN）、作者自检范围与结论、旧 URL 兼容性、剩余风险**。不得把 PR Ready、CI PASS 或摘要当作网站质量 PASS。

## README 与公开首页

编辑 README.md 或 content/index.md 时，先把它们当作第一次到访的读者会看到的项目门面：说明这是什么、从哪里开始读、怎样贡献以及内容许可。不要把 Agent 工作流、Kody/CI/Pages/HTTPS 门禁、PR 历史、重构台账或管理员命令搬进公开页面；这些内容留在相应维护文档。开发者首页也应优先提供技术阅读路线，避免内部协调信息污染正文。完成后检查实际 HTML，而不只检查 Markdown 源文件。
## 导航状态与空菜单门禁

`ordered-explorer` 的正式分类首次加载必须完整展开；`useSavedState` 必须保持读者主动调整的目录状态，SPA 切换只展开当前页面祖先，不得重置其他目录。没有真实下级正式页面的节点必须降级为普通链接。`scripts/check-navigation.mjs` 同时检查源模型、全部条目索引和构建后的导航 DOM；失败时不得发布。

标签不是主导航分类：保留标签元数据、索引页面和既有 URL，但从导航数据模型排除 `tags/` 及其子节点，不得用折叠或 CSS 隐藏。AI 草稿、历史归档、内部索引、生成目录和虚拟目录也不得污染 Explorer。CI 必须在构建前后检查桌面与移动 DOM，确认辅助页面没有导航节点。

标题门禁由 `scripts/check-title-length.mjs` 强制执行：导航分类最多 8 字，H1 最多 16 字，H2 最多 12 字，H3/H4 最多 16 字；教程、攻略和故障排查 H1 最多 20 字，侧栏显示名最多 12 字。中文及全角字符按 1 字、半角英文/数字/符号按 0.5 字折算；原版译文前缀不计入条目名但不豁免侧栏显示名。脚本和构建后门禁报告文件、行号、实际长度和上限，超限直接失败；内容质量恢复阶段不得用截短、批量例外或删除正文知识消除违规，例外必须逐项登记理由并由 Lead 复审。Lead 仍须在桌面和移动视口实际检查标题、面包屑和目录的可读性。

## 全站字体验收

普通正文、标题、导航、搜索、表格、引用、链接及行内科学记数法统一继承系统无衬线字体；纯数字记数法（如 `1.80e308`）使用普通文本，含运算结构的真正数学公式才使用 KaTeX；程序代码使用系统等宽字体。不得引入 Google Fonts、Quartz 网页字体或其他固定网页字体。除 `check-fonts.mjs` 的源代码和构建产物门禁外，Lead 必须用 Playwright Android Chrome 视口读取实际 computed style，至少覆盖玩家、开发者、原版译文、表格、数学表达式和代码块，并查看修改前后截图；CI 通过不等于视觉验收通过。

`scripts/acceptance-fonts.cjs` 会强制检查正文、标题、导航、搜索框、表格、代码块和数学表达式样本实际存在，验证每个样本的系统字体类别并断言 HTTP 200。默认目标是本地预览（`KB_URL=http://127.0.0.1:8080`）；完成部署后，只有明确设置 `KB_URL=https://wiki.oreki.net KB_ALLOW_PRODUCTION=1` 才能验收线上版本，避免把旧线上站点当作当前候选构建。

```text
KB_URL=http://127.0.0.1:8080 KB_FONT_OUT=evidence/playwright-fonts.json node scripts/acceptance-fonts.cjs
KB_URL=https://wiki.oreki.net KB_ALLOW_PRODUCTION=1 KB_FONT_OUT=evidence/playwright-fonts-live.json node scripts/acceptance-fonts.cjs
```
