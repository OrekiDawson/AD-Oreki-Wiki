## 重构目标与先后次序

按用户真正会做的事设计开发者阅读路径，而不是按 Agent 输出组织文章。

本专区的正式正文是技术百科与知识库，不是开发日志、周报、审计报告或 Agent 工作记录。所有尚未按新标准完成的页面直接从源码、构建链和原始资料重新撰写；不得按 R/日期/PR 罗列过程，堆砌状态、SHA、Issue 或路径，或把规则、任务书、验收报告换写成文章。流水账统一归入历史档案，正文必须解释机制、设计、难点、使用修改排查方法和可迁移经验。

“作者化表达”是独立验收字段，不与正文修改状态、Lead 正文复审、合并或上线状态合并。原创技术文章按“待评估 / 不合格 / 整改中 / 待复审 / 合格”记录；原版忠实译文等不适用页面记录“不适用”。CI、Kody、合并和上线通过均不能自动推导作者化表达合格。

1. **第一批：入口和入门**。开发者首页先能找到“如何从零参与一个小任务”，再理解主仓结构。至少有一条完整可审校的上手路径。
2. **第二批：架构与代码定位**。Android/Web 分别讲清真实模块、数据流和源代码入口，调度器、存档和阶段门禁等由单一准确参考承担；不堆历史 PR。
3. **第三批：构建与验证**。AGP 与 CI/CD 指南核验实际入口、权限、输入、命令、产物、失败原因；未执行命令不得宣称可用或 PASS。
4. **第四批：典型排障、状态与导航收口**。用真实且脱敏的案例指导定位，状态页重新核对当前来源；历史与 AI Summary 退出主导航、保留辅助查阅。
5. **其余资料**按真实读者问题逐篇分类为教程/操作/参考/原理/档案，选“保留、精修、归档、合并并保留 alias”，无证据不机械删除。

每批的正常流程：读实际来源 → 从零重写正文 → 作者事实与技术自检 → Lead 逐篇完整阅读最终正文并必要整改 → 最小相关检查 → Kody/CI → 合并 → 站点/旧 URL 验证。旧稿只作事实线索，历史档案、原始证据、版权与旧 URL 继续保留。未经 Lead 正文复审或发现实际事实错误、无法操作、版权问题均记 `EDITORIAL_BLOCKED`，不得合并/发布；Lead 自己撰写的文章执行作者自检。游戏真实长跑、APK Release 不是纯 Wiki 文档 PR 的默认附属任务。
